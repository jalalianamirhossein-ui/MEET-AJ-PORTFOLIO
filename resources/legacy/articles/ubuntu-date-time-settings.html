Configure Ubuntu Time Synchronization with Chrony

Configure internal NTP, inspect offset and reach, select Asia/Tehran and investigate VM clock jumps.

Linux

Meet AJ technical article

Start reading

Clock time and timezone are different

Timezone changes display. Chrony synchronizes the underlying clock through NTP. For TLS or Kerberos failures, inspect clock, sources and offset. Switching Asia/Tehran to UTC does not itself correct clock skew.

Sources, kernel clock and applications

Chronyd uses source measurements to correct kernel-clock error. Applications read system time, while timezone controls display. Abrupt clock steps affect scheduling and databases.

Example: two internal sources

Servers use 10.20.30.53 and 10.20.30.54, with central logs in UTC. Sources need independent dependencies. Two disagreeing sources do not establish which is correct. Design additional source diversity for fault tolerance.

Time daemon and NTP reachability

The example uses Ubuntu 24.04 LTS and Chrony. Record the installed version and active time daemon.

No special compute capacity is needed. In VMs, inspect hypervisor synchronization so competing mechanisms do not repeatedly change the clock.

Prepare sudo and UDP/123 access to real sources, replacing sample addresses. NTS also requires supported sources and its separate TLS path.

Chrony and timesyncd

timesyncd is another option for simple clients. Chrony owns synchronization here. Timedatectl timesync-status reports timesyncd. Use sources and tracking for Chrony.

Restrict NTP and review clock steps

Restrict sources to approved destinations and avoid unintentionally exposing a public NTP server. Inspect existing makestep before restart. Restart resets the update count, so startup policy might step time without a manual makestep command.

Configure sources and verify synchronization

Record the current state. Only one daemon should own synchronization. Installing chrony normally replaces timesyncd, but verify the resulting service states. 

timedatectl status
date -u --iso-8601=seconds
sudo apt-get update
sudo apt-get install -y chrony
systemctl is-active chrony systemd-timesyncd
sudo cp -a /etc/chrony /root/chrony-before-change

Review existing pool/server lines and generated sourcedir entries in /etc/chrony/chrony.conf. Remove conflicting sources only after identifying their ownership. These complete source lines replace public sources with approved internal ones. 

server 10.20.30.53 iburst
server 10.20.30.54 iburst
sudo chronyd -p -f /etc/chrony/chrony.conf
sudo systemctl restart chrony
chronyc sources -v
chronyc tracking
sudo timedatectl set-timezone Asia/Tehran
date -u --iso-8601=seconds

Expect a source marked ^*, Reach approaching 377 over multiple polls and Leap status: Normal. Reverse DNS may change the displayed source name. Do not run makestep on production with a large offset until its effects on databases and scheduling have been assessed.

Before restart, inspect the printed configuration for makestep and DHCP-supplied sources. If abrupt correction is unacceptable, align policy with the workload and use an appropriate maintenance window.

Offsets and the selected source

Monitor offset, stratum, reach and source changes. A 100 ms offset for five minutes is an example threshold to align with application needs. Active Chrony does not establish synchronization.

Zero reach or clock jumps

^? marks a currently unusable source. Check UDP, DNS and its clock. ^x marks a source identified as a falseticker. 

chronyc sources -v
chronyc sourcestats -v
chronyc tracking
sudo journalctl -u chrony -n 80 --no-pager

Zero reach means no successful polls were recorded. Repeated VM jumps require comparing host sync, guest daemon and step policy. Diagnose certificate expiry from clock time and notAfter, not timezone.

Restore sources before sensitive workloads

Version configuration, source inventory and timezone. Restore prior settings after reviewing step policy and inspect tracking. Confirm synchronization after long downtime before starting sensitive workloads.

UTC records and local display

Use UTC for logs and suitable local display for users. Assess workload effects of manual clock or source changes. Avoid unplanned production steps for large offsets.

Frequently Asked Questions

Does a wrong timezone cause TLS failure?

TLS relies on the actual clock. Timezone settings change only its display.

Does an active chrony service mean it is synchronized?

No. Check selected sources, offset and Leap status.
