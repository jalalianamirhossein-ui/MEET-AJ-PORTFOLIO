Windows Server DFS: Namespace, Replication and Recoverable File Services

Deploy domain-based DFS-N and DFS-R with reviewed permissions, initial-sync acceptance, backlog monitoring and independent file backups.

Microsoft

Meet AJ technical article

Start reading

Introduction

Namespace provides a stable path; Replication copies files. Neither is a backup. Deletions and overwrites can propagate to other members.

Practical Example

Two branches use Company/Data. FS01 supplies initial content to FS02. Users must not write to FS02 before initial synchronization finishes.

Prerequisites

Windows Server 2022/2025 joined to AD DS with DFSN/DFSR PowerShell modules. Replicated content uses NTFS; DFS-R does not support ReFS.

Two file servers with separate storage. Size staging from the largest files and allow space for conflict/deleted content; inventory determines capacity.

Role-installation rights on both servers and delegated AD namespace/replication access. Prepare SMB/NTFS. The example assumes corp.example.com, FS01/FS02 and existing D: volumes.

Architecture / Design

Client → AD referral/DFS-N → SMB target. Separately, DFS-R replicates closed files between members. Multi-master replication does not provide cross-site file locking.

Installation / Configuration

Prepare roles and paths on both file servers. D: must be suitable NTFS storage. CORP FileUsers represents the actual organizational group.

Install-WindowsFeature FS-DFS-Namespace,FS-DFS-Replication -IncludeManagementTools
New-Item -ItemType Directory -Path 'D:\DFSRoots\Company','D:\Data' -Force | Out-Null
New-SmbShare -Name Company -Path 'D:\DFSRoots\Company' -ReadAccess 'CORP\FileUsers'
New-SmbShare -Name Data -Path 'D:\Data' -ChangeAccess 'CORP\FileUsers'
Get-WindowsFeature FS-DFS-Namespace,FS-DFS-Replication

Design/apply NTFS ACLs with the data owner; share permissions do not grant NTFS access. Continue from a management host with modules and delegation.

Import-Module DFSN
Import-Module DFSR
New-DfsnRoot -Path '\\corp.example.com\Company' -TargetPath '\\FS01\Company' -Type DomainV2
New-DfsnRootTarget -Path '\\corp.example.com\Company' -TargetPath '\\FS02\Company'
New-DfsnFolder -Path '\\corp.example.com\Company\Data' -TargetPath '\\FS01\Data'
New-DfsnFolderTarget -Path '\\corp.example.com\Company\Data' -TargetPath '\\FS02\Data' -State Offline
New-DfsReplicationGroup -GroupName 'Company-Data'
New-DfsReplicatedFolder -GroupName 'Company-Data' -FolderName 'Data'
Add-DfsrMember -GroupName 'Company-Data' -ComputerName 'FS01','FS02'
Add-DfsrConnection -GroupName 'Company-Data' -SourceComputerName 'FS01' -DestinationComputerName 'FS02'
Set-DfsrMembership -GroupName 'Company-Data' -FolderName 'Data' -ComputerName 'FS01' -ContentPath 'D:\Data' -PrimaryMember $true -Force
Set-DfsrMembership -GroupName 'Company-Data' -FolderName 'Data' -ComputerName 'FS02' -ContentPath 'D:\Data' -Force

Add-DfsrConnection creates the reverse connection by default; inspect Get-DfsrConnection. Do not repeat creation on existing deployments. AD propagation/initial sync takes time. PrimaryMember selects the initial source only. FS02 starts Offline so clients receive no referrals before acceptance; also restrict direct user access to its share during initial sync. Accept only after a closed canary file reaches FS02 with the same hash and both backlogs reach zero. Run the following commands to bring that target Online only after these checks pass.

Set-DfsnFolderTarget -Path '\\corp.example.com\Company\Data' -TargetPath '\\FS02\Data' -State Online
Get-DfsnFolderTarget -Path '\\corp.example.com\Company\Data'

Security Hardening

Scope SMB and RPC/DFSR to members and consumer subnets using official Windows Firewall guidance. Coordinate dynamic RPC ranges with policy. Review share/NTFS ACLs, SMB signing and access audit. End users should not write to the namespace root.

Monitoring

Monitor both backlog directions, DFS Replication logs, staging pressure, disk space and conflict/deleted content. Short backlogs can be normal; sustained growth matters. Specify the monitoring account context for Zabbix checks.

Troubleshooting

A healthy namespace with old files calls for separate DFS-R/backlog investigation. Run these diagnostics from a module-equipped host.

Get-DfsrConnection -GroupName 'Company-Data'
Get-DfsrBacklog -GroupName 'Company-Data' -FolderName 'Data' -SourceComputerName 'FS01' -DestinationComputerName 'FS02' -Verbose
Get-DfsrBacklog -GroupName 'Company-Data' -FolderName 'Data' -SourceComputerName 'FS02' -DestinationComputerName 'FS01' -Verbose
Get-WinEvent -LogName 'DFS Replication' -MaxEvents 30
Test-NetConnection FS02 -Port 445

The backlog cmdlet displays a limited list; inspect verbose output for the full count. Open files/databases may not replicate. Inspect events for staging/content-freshness issues. Do not delete the DFS-R database as a generic fix.

Backup / Recovery

Use independent VSS-aware file and AD/namespace backups with off-site/immutable copies. Control overwrite propagation during restore: recover to an isolated path, compare ACL/hash, then return selected files through a change record. Rebuild failed members and use documented non-authoritative sync. Do not mark both members primary. RPO depends on actual backups, not DFS-R speed.

Best Practices

Use DFS-R for closed files and compatible workflows. Live databases, active VM disks and cross-branch locking workloads are unsuitable here. Accept initial sync before sending user referrals.

Legacy Versions and Compatibility

DFS-N and DFS-R are separate roles. This is a domain-based namespace; standalone HA differs. Replicated volumes use NTFS in this baseline.

Frequently Asked Questions

Is DFS-R a backup replacement?

No. Deletes/overwrites can replicate; independent backups remain necessary.

Is PrimaryMember a permanent leader?

No. It selects the initial-sync source; normal replication is multi-master.
