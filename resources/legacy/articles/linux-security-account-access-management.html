Linux Accounts and Restricted sudo Access

Create a restricted account, validate exact sudo rules and revoke keys, credentials and sessions during offboarding.

Authentication and command privileges differ

Linux accounts, login methods and sudo privileges are separate controls. Grant support users only the necessary command and test denied operations too. During offboarding, password locking alone is insufficient. Review keys, tokens and active sessions.

From groups to exact sudo rules

Identity and groups control admission. Sudo specifies permitted commands. Separate human and service accounts, and assign rotatable automation credentials with accountable owners.

Example: inspect Nginx without restart rights

opsreader reads only nginx.service status. It is not a sudo-group member and receives a dedicated rule. Status inspection must work while restart and unit editing remain denied.

Local account and administrator access

Commands target Ubuntu 24.04 LTS with sudo and OpenSSH. Check the local systemctl path. For LDAP or SSSD users, also inspect organizational identity policy.

No extra compute allocation is required. Keep an administrator console and known-good sudoers configuration for policy recovery.

opsreader is an example name. Check account existence and group memberships first. A restricted rule does not cancel broader privileges granted by another group.

sudo membership and password locks

usermod -aG sudo usually grants broad access and does not fit this status-only role. Passwd -l locks the password. Disabling every login path also involves SSH and identity policy.

Create the account and validate the rule

Check account existence first. Create the sample account without sudo-group membership if absent. Identify systemctl’s path before writing the rule. 

getent passwd opsreader
sudo adduser opsreader
id opsreader
command -v systemctl
sudo visudo -f /etc/sudoers.d/opsreader-nginx

This is the complete rule. Match the binary path to the host. --no-pager avoids interactive-pager shell escapes. 

opsreader ALL=(root) /usr/bin/systemctl --no-pager status nginx.service
sudo chmod 440 /etc/sudoers.d/opsreader-nginx
sudo visudo -cf /etc/sudoers
sudo -l -U opsreader
sudo -u opsreader sudo /usr/bin/systemctl --no-pager status nginx.service

Expect valid syntax from visudo and only the intended grant from sudo -l. Inactive Nginx gives status a nonzero code. In staging, test restart denial and distinguish it from a service error.

Privilege failure or service failure?

Start with sudo -l and validate syntax using visudo -cf. Status returns nonzero for inactive services without implying denied privileges. Login with a locked password might use a key or another method. 

sudo -l -U opsreader
sudo chage -l opsreader
loginctl list-sessions
getent group sudo
sudo journalctl _COMM=sudo -n 50 --no-pager

Compare current session groups with new policy. Identity caches and existing sessions might delay changes. Confirm UID and running jobs before terminating sessions.

Restricted commands and escape paths

Shells, editors and package managers often execute root code. Broad wildcards are not restricted privileges. --no-pager keeps the example out of an interactive pager. Avoid unnecessary interactive service-account login. Revoke keys, directory access, API tokens, cron, sudo and sessions independently.

Audit account and privilege changes

Retain sudo and SSH events centrally. Audit changes to passwd, group and sudoers.d with appropriate policy. Compare UID-zero accounts against the approved list.

Undo a rule and retain user data

Remove the dedicated file from sudoers.d and rerun visudo to revoke the grant. Version UID/GID mappings and policy. Encrypt shadow and key backups. During offboarding, revoke access before removing HOME, following retention and data-handover requirements.

Positive and negative permission tests

Test permitted and forbidden commands as the target user in staging. Keep emergency credentials in a vault and rule changes in access-management records.

Frequently Asked Questions

Does passwd -l disable an SSH key?

No. Keys and other credentials require separate revocation.

Why include --no-pager in a sudo rule?

A pager may provide a shell using the privileges of the invoking command.
