Install NetBox on Ubuntu with PostgreSQL and Nginx

Install NetBox 4.7.2, configure its database, Redis and Gunicorn, verify API/workers, and test backup and restore.

NetBox as a network source of truth

NetBox records devices, addresses, prefixes, VLANs and their relationships. Reliable inventory needs more than a working UI. Configure API permissions, workers and recovery of database/files. This example takes a single-server deployment through practical validation.

Web service, database and worker

Nginx forwards HTTPS to loopback Gunicorn. NetBox stores data in PostgreSQL and workers use Redis for jobs. Tasks and cache use separate Redis databases here. Protect database, media, configuration and secrets together.

Example: inventory for three datacenters

The network-owner group maintains devices/prefixes. Automation reads with restricted tokens, while defined roles control writes. Test with one site/prefix and confirm a read-only identity’s write request is rejected.

Baseline versions and hostname

The baseline is NetBox 4.7.2 on Ubuntu 24.04 LTS with Python 3.12, PostgreSQL 16 and Redis 7. Check plugins and that release’s requirements before execution.

Four vCPUs, 8 GiB RAM and 60 GiB SSD are example starting allocations. Measure database/media growth and job load. This single-node design does not implement HA.

Prepare sudo, actual DNS, a trusted certificate and dedicated PostgreSQL identity. Replace netbox.example.com in configuration and Nginx. Generate new SECRET_KEY and pepper values for this installation.

Release-specific configuration

This configuration targets 4.7.2. Match DATABASES, API_TOKEN_PEPPERS and token behavior to that release. This procedure uses Git. Python-package installation is experimental in 4.7.

Install dependencies and start services

Use a fresh VM with local DB. Install dependencies and record versions first. This does not perform an automatic full OS upgrade. 

sudo apt-get update
sudo apt-get install -y postgresql redis-server python3 python3-venv python3-dev build-essential libxml2-dev libxslt1-dev libffi-dev libpq-dev libssl-dev zlib1g-dev git nginx
python3 --version
psql --version
redis-cli ping
sudo -u postgres createuser netbox
sudo -u postgres psql -c '\password netbox'
sudo -u postgres createdb -O netbox netbox
sudo -u postgres psql -d netbox -c 'GRANT CREATE ON SCHEMA public TO netbox;'
sudo git clone --branch v4.7.2 --depth 1 https://github.com/netbox-community/netbox.git /opt/netbox
sudo adduser --system --group netbox
sudo chown -R netbox:netbox /opt/netbox/netbox/media /opt/netbox/netbox/reports /opt/netbox/netbox/scripts

The password command prompts interactively. Reuse that value in configuration. Createuser/createdb are for a fresh installation only. Keep Redis on loopback. Generate the complete configuration with Python, entering the DB password at its prompt and replacing the sample hostname first. 

sudo python3 - <<'PY'
from pathlib import Path
import getpass, secrets
db_password = getpass.getpass('PostgreSQL netbox password: ')
host = 'netbox.example.com'  # Replace with the real DNS hostname before running.
if not host or '/' in host or '*' in host:
    raise SystemExit('Use one explicit DNS hostname')
config = {
    'ALLOWED_HOSTS': [host],
    'DATABASES': {'default': {'NAME':'netbox','USER':'netbox','PASSWORD':db_password,'HOST':'127.0.0.1','PORT':'5432','CONN_MAX_AGE':300}},
    'REDIS': {'tasks': {'HOST':'127.0.0.1','PORT':6379,'DATABASE':0,'SSL':False}, 'caching': {'HOST':'127.0.0.1','PORT':6379,'DATABASE':1,'SSL':False}},
    'SECRET_KEY': secrets.token_urlsafe(64),
    'API_TOKEN_PEPPERS': {1:secrets.token_urlsafe(64)},
    'CSRF_TRUSTED_ORIGINS': ['https://' + host],
}
path = Path('/opt/netbox/netbox/netbox/configuration.py')
if path.exists():
    raise SystemExit('Configuration already exists; review it')
path.write_text('\n'.join(f'{k} = {v!r}' for k,v in config.items())+'\n')
PY
sudo chown root:netbox /opt/netbox/netbox/netbox/configuration.py
sudo chmod 640 /opt/netbox/netbox/netbox/configuration.py
sudo /opt/netbox/upgrade.sh
sudo -u netbox /opt/netbox/venv/bin/python /opt/netbox/netbox/manage.py check
sudo -u netbox /opt/netbox/venv/bin/python /opt/netbox/netbox/manage.py createsuperuser
sudo cp /opt/netbox/contrib/gunicorn.py /opt/netbox/gunicorn.py
sudo cp /opt/netbox/contrib/netbox.service /opt/netbox/contrib/netbox-rq.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now netbox netbox-rq

Checks must pass without errors and services must be active. Contrib Gunicorn normally binds 127.0.0.1:8001. Inspect its file and ss. Write this complete Nginx configuration with the real hostname/certificate. Static alias must reference the same checkout. 

server {
    listen 443 ssl;
    server_name netbox.example.com;
    ssl_certificate /etc/nginx/tls/fullchain.pem;
    ssl_certificate_key /etc/nginx/tls/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    client_max_body_size 25m;
    location /static/ { alias /opt/netbox/netbox/static/; }
    location / {
        proxy_pass http://127.0.0.1:8001;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

Save as sites-available/netbox, create the initial symlink, run nginx -t and reload. Certificates must exist before testing. Test curl --fail https://netbox.example.com/login/, login and API reads with a restricted token. Create a sample site/prefix in UI and verify read-only write denial.

API permissions and secret protection

Keep PostgreSQL/Redis off public interfaces. Restrict API tokens by role and expiry, and avoid daily superuser use. Retain SECRET_KEY/API_TOKEN_PEPPERS in encrypted backups. Unplanned rotation affects credentials and sessions.

Healthy UI with stalled jobs

Probe login and API reads through the real path. Monitor netbox-rq, queue age, database load, disks and certificates separately. Active Nginx does not prove jobs execute. Restrict metrics to monitoring networks.

502, CSRF and queue failures

For 502, inspect Gunicorn bind and logs. DisallowedHost requires matching ALLOWED_HOSTS. For CSRF 403, check origin and X-Forwarded-Proto. Pending jobs require Redis tasks and netbox-rq checks. 

systemctl is-active postgresql redis-server netbox netbox-rq nginx
sudo journalctl -u netbox -u netbox-rq -n 100 --no-pager
sudo ss -lntp
redis-cli ping
sudo -u netbox /opt/netbox/venv/bin/python /opt/netbox/netbox/manage.py check

Keep secret-bearing configuration out of public tickets. After upgrades, inspect plugins, release notes and migration logs. Deleting migration history is not an upgrade repair.

Coordinated backup and isolated restore

Daily backups target the example 24-hour RPO. Coordinate database/media by stopping relevant writers and jobs during backup. Design PostgreSQL PITR separately for a shorter RPO. 

sudo install -d -m 700 /var/backups/netbox
sudo bash -c 'umask 077; sudo -u postgres pg_dump -Fc netbox > /var/backups/netbox/netbox.dump'
sudo bash -c 'umask 077; tar -czf /var/backups/netbox/application-state.tar.gz -C /opt/netbox netbox/media netbox/reports netbox/scripts netbox/netbox/configuration.py'
sudo chmod 600 /var/backups/netbox/application-state.tar.gz

The example redirects within a root-authorized shell. Copy files off-host to protected storage. Restore on an isolated server with matching version/plugins. 

sudo -u postgres createdb -O netbox netbox_restore
sudo bash -c 'sudo -u postgres pg_restore --no-owner --role=netbox -d netbox_restore < /var/backups/netbox/netbox.dump'
sudo -u postgres psql -d netbox_restore -c 'SELECT count(*) FROM dcim_site;'

Point destination configuration at netbox_restore and restore media, secrets and peppers. Disable outbound webhooks/automation. Test login, object counts, API and a canary job, recording restore duration. Code-only rollback after migrations is insufficient.

The archive also retains custom reports and scripts. Keep the restored environment from sending production jobs to real devices.

Data ownership and upgrades

NetBox is not an NMS or automatic discovery tool. Assign inventory owners and update procedures. Pin versions/plugins and test migrations in staging with a restorable backup.

Frequently Asked Questions

Is a PostgreSQL backup enough?

No. Retain media, configuration, secret key, pepper and plugin versions.

Can code simply be downgraded after a migration?

No. Rollback must account for schema compatibility and the pre-change database backup.
