NetBox 4.7.2 on Ubuntu: Secure Deployment, API Access and Restore

Deploy a pinned NetBox baseline with PostgreSQL, Redis and TLS, then test least-privilege API access, worker health and isolated recovery.

NetBox

Meet AJ technical article

Start reading

Introduction

NetBox is a network source of truth. Database loss or excessive API permissions can disrupt inventory and automation. Installation must include identity policy and a testable restore.

Practical Example

Networking records three datacenters, VLANs and prefixes. Automation receives read access; inventory-owner groups control writes.

Prerequisites

Baseline: Ubuntu Server 24.04 LTS, NetBox 4.7.2, Python 3.12, PostgreSQL 16 and Redis 7. Pin patches/plugins after staging tests.

Example capacity: 4 vCPU, 8 GiB RAM, 60 GiB SSD. Measure database/media growth, object count and job load. This single node is not a complete HA implementation.

sudo, git, apt, dedicated PostgreSQL identity, DNS and PKI for the real hostname replacing netbox.example.com. Generate fresh SECRET_KEY and pepper values.

Architecture / Design

HTTPS/Nginx → loopback Gunicorn → Django/NetBox → PostgreSQL. netbox-rq uses Redis tasks; cache and queue are separate. Protect DB, media, configuration and secrets together.

Installation / Configuration

Use a fresh VM with local DB. Install dependencies and record versions first; this does not perform an automatic full OS upgrade.

sudo apt-get update
sudo apt-get install -y postgresql redis-server python3 python3-venv python3-dev build-essential libxml2-dev libxslt1-dev libffi-dev libpq-dev libssl-dev zlib1g-dev git nginx
python3 --version
psql --version
redis-cli ping
sudo -u postgres createuser netbox
sudo -u postgres psql -c '\password netbox'
sudo -u postgres createdb -O netbox netbox
sudo -u postgres psql -d netbox -c 'GRANT CREATE ON SCHEMA public TO netbox;'
sudo git clone --branch v4.7.2 --depth 1 https://github.com/netbox-community/netbox.git /opt/netbox
sudo adduser --system --group netbox
sudo chown netbox:netbox /opt/netbox/netbox/media

The password command prompts interactively; reuse that value in configuration. createuser/createdb are for a fresh installation only. Keep Redis on loopback. Generate the complete configuration with Python, entering the DB password at its prompt and replacing the sample hostname first.

sudo python3 - <<'PY'
from pathlib import Path
import getpass, secrets
db_password = getpass.getpass('PostgreSQL netbox password: ')
host = 'netbox.example.com'  # Replace with the real DNS hostname before running.
if not host or '/' in host or '*' in host:
    raise SystemExit('Use one explicit DNS hostname')
config = {
    'ALLOWED_HOSTS': [host],
    'DATABASES': {'default': {'NAME':'netbox','USER':'netbox','PASSWORD':db_password,'HOST':'127.0.0.1','PORT':'5432','CONN_MAX_AGE':300}},
    'REDIS': {'tasks': {'HOST':'127.0.0.1','PORT':6379,'DATABASE':0,'SSL':False}, 'caching': {'HOST':'127.0.0.1','PORT':6379,'DATABASE':1,'SSL':False}},
    'SECRET_KEY': secrets.token_urlsafe(64),
    'API_TOKEN_PEPPERS': {1:secrets.token_urlsafe(64)},
    'CSRF_TRUSTED_ORIGINS': ['https://' + host],
}
path = Path('/opt/netbox/netbox/netbox/configuration.py')
if path.exists():
    raise SystemExit('Configuration already exists; review it')
path.write_text('\n'.join(f'{k} = {v!r}' for k,v in config.items())+'\n')
PY
sudo chown root:netbox /opt/netbox/netbox/netbox/configuration.py
sudo chmod 640 /opt/netbox/netbox/netbox/configuration.py
sudo /opt/netbox/upgrade.sh
sudo -u netbox /opt/netbox/venv/bin/python /opt/netbox/netbox/manage.py check
sudo -u netbox /opt/netbox/venv/bin/python /opt/netbox/netbox/manage.py createsuperuser
sudo cp /opt/netbox/contrib/gunicorn.py /opt/netbox/gunicorn.py
sudo cp /opt/netbox/contrib/netbox.service /opt/netbox/contrib/netbox-rq.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now netbox netbox-rq

Checks must pass without errors and services must be active. Contrib Gunicorn normally binds 127.0.0.1:8001; inspect its file and ss. Write this complete Nginx configuration with the real hostname/certificate; static alias must reference the same checkout.

server {
    listen 443 ssl;
    server_name netbox.example.com;
    ssl_certificate /etc/nginx/tls/fullchain.pem;
    ssl_certificate_key /etc/nginx/tls/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    client_max_body_size 25m;
    location /static/ { alias /opt/netbox/netbox/static/; }
    location / {
        proxy_pass http://127.0.0.1:8001;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

Save as sites-available/netbox, create the initial symlink, run nginx -t and reload. Certificates must exist before testing. Test curl --fail https://netbox.example.com/login/, login and API reads with a restricted token. Create a sample site/prefix in UI and verify read-only write denial.

Security Hardening

Do not bind PostgreSQL/Redis to WAN. Allow organizational HTTPS and management SSH only. Preserve SECRET_KEY/API_TOKEN_PEPPERS in encrypted backups; unplanned rotation can invalidate credentials. Use object permissions, token expiry, SSO/MFA and separate superusers.

Monitoring

Monitor login/API probes, worker state, queue age, DB connections, disk and certificate expiry. Restrict metrics endpoints to monitoring. Active Nginx does not establish job completion.

Troubleshooting

For 502, inspect Gunicorn bind/service logs. DisallowedHost requires the real ALLOWED_HOSTS. CSRF 403 requires checking trusted origin and forwarded protocol. Pending jobs require Redis tasks/netbox-rq checks.

systemctl is-active postgresql redis-server netbox netbox-rq nginx
sudo journalctl -u netbox -u netbox-rq -n 100 --no-pager
sudo ss -lntp
redis-cli ping
sudo -u netbox /opt/netbox/venv/bin/python /opt/netbox/netbox/manage.py check

Do not publish secret-bearing configuration in public tickets. After upgrades, investigate plugin compatibility/release notes; deleting migration history is not a repair.

Backup / Recovery

For a sample 24-hour RPO, use daily database/media/config backups and off-host copies. If media/config are changing, run this export in maintenance without writers. Design PostgreSQL PITR for shorter RPO.

sudo install -d -m 700 /var/backups/netbox
sudo bash -c 'umask 077; sudo -u postgres pg_dump -Fc netbox > /var/backups/netbox/netbox.dump'
sudo tar -czf /var/backups/netbox/application-state.tar.gz -C /opt/netbox netbox/media netbox/netbox/configuration.py
sudo chmod 600 /var/backups/netbox/application-state.tar.gz

Redirection occurs inside the root shell; sudo pg_dump followed by shell redirection alone cannot write a protected path. Transfer the backup to a vault/off-host and record hashes. Restore on an isolated server with matching version/plugins, never the primary DB.

sudo -u postgres createdb -O netbox netbox_restore
sudo bash -c 'sudo -u postgres pg_restore --no-owner --role=netbox -d netbox_restore < /var/backups/netbox/netbox.dump'
sudo -u postgres psql -d netbox_restore -c 'SELECT count(*) FROM dcim_site;'

Point restore configuration at netbox_restore, restore SECRET_KEY/pepper/media, and disable outgoing automation/webhooks. Validate login, object counts, API and a canary job; measure RTO. Code-only downgrade after migrations is invalid.

Best Practices

Lock versions/plugins, stage migrations, back up before upgrades and test restore. NetBox is neither discovery nor an NMS; inventory needs accountable owners.

Legacy Versions and Compatibility

4.7.2 is this guide’s baseline, not a guarantee for future patches. Python-package installation is experimental in 4.7; use Git/archive here. Match legacy API tokens and newer Bearer usage to the token version.

Frequently Asked Questions

Is a PostgreSQL backup enough?

No. Retain media, configuration, secret key, pepper and plugin versions.

Can code simply be downgraded after a migration?

No. Rollback must account for schema compatibility and the pre-change database backup.
