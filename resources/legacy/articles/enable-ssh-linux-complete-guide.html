Production SSH: Key Authentication, Security Hardening and Access Recovery

Configure production SSH with key authentication, bastion access, effective configuration checks, independent login validation and a tested rollback path.

Linux

Meet AJ technical article

Start reading

Introduction

An authentication change can leave a healthy server unreachable by the operations team. This runbook pairs access controls with an independent login test and a recovery path.

Practical Example

Operations manages 40 VMs through a bastion on 10.20.30.0/24. Public Internet login is blocked, and changes reach a canary first.

Prerequisites

Ubuntu Server 24.04 LTS, Bash 5 and systemd. Record installed package patches with dpkg-query before making changes.

Example lab capacity: 2 vCPUs, 2 GiB RAM and 20 GiB storage. These are planning assumptions, not vendor minimums; size the service for measured load.

Install openssh-server on the server and openssh-client on the workstation. Authorized sudo and console access are required. Replace opsadmin and 10.20.30.10 with approved account and address values.

Architecture / Design

Workstation → VPN/MFA → bastion → management Firewall → sshd → personal account → sudo. Keep the private key on the workstation and verify the server fingerprint through the console.

Installation / Configuration

Record the version, listener and service state first. Install only the SSH package; do not combine this change with a full system upgrade.

sudo apt-get update
sudo apt-get install -y openssh-server
dpkg-query -W openssh-server
systemctl status ssh.service ssh.socket --no-pager
sudo ss -lntp '( sport = :22 )'
sudo cp -a /etc/ssh /root/ssh-before-change

On the workstation, generate a passphrase-protected key and install it for an account that already exists. Compare the host fingerprint before accepting the connection.

ssh-keygen -t ed25519 -f "$HOME/.ssh/ops_ed25519"
ssh-copy-id -i "$HOME/.ssh/ops_ed25519.pub" opsadmin@10.20.30.10
ssh -i "$HOME/.ssh/ops_ed25519" -o PasswordAuthentication=no opsadmin@10.20.30.10

On the server, inspect ownership and permissions as that account. After the second session succeeds, write the configuration from an authorized sudo session.

chmod 700 "$HOME/.ssh"
chmod 600 "$HOME/.ssh/authorized_keys"
sudo tee /etc/ssh/sshd_config.d/00-enterprise.conf >/dev/null <<'EOF'
PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
AllowUsers opsadmin
X11Forwarding no
MaxAuthTries 3
EOF
sudo /usr/sbin/sshd -t
sudo /usr/sbin/sshd -T | grep -E 'permitrootlogin|passwordauthentication|allowusers'
sudo systemctl reload ssh.service

Successful sshd -t produces no output. Effective configuration from -T must show passwordauthentication no. Keep the first session open and verify key login plus sudo in a third session. Include all required human and automation accounts in AllowUsers before deployment.

Security Hardening

Restrict upstream TCP/22 access to the bastion. The example ufw allow from 10.20.30.0/24 to any port 22 proto tcp applies only to an existing UFW deployment; do not enable an unplanned Firewall remotely. Changing the port does not replace authentication. Use MFA on the bastion. If SSH itself uses PAM MFA, reconcile KbdInteractiveAuthentication no with that design. Under FIPS policy, check Ed25519 acceptance and use RSA with SHA-2 signatures where required.

Monitoring

Use journalctl -u ssh.service --since "15 minutes ago" to investigate logins. Monitor TCP availability and authorized login separately in Zabbix. More than 10 failed logins in five minutes is an illustrative threshold. Include hostname, source IP and UTC time in alerts; exclude private keys and tokens.

Troubleshooting

Connection refused points to a listener or reject response; timeouts more often indicate routing or dropped traffic. Inspect the server and client independently with these commands.

sudo journalctl -u ssh.service -n 100 --no-pager
sudo /usr/sbin/sshd -T
ssh -vvv -i "$HOME/.ssh/ops_ed25519" opsadmin@10.20.30.10

For Permission denied with bad ownership in the log, correct HOME and .ssh ownership. If a valid key is rejected, inspect AllowUsers, Match blocks and effective configuration using -T -C. Ubuntu may use ssh.socket; a port change requires checking both sshd and its socket listener for that patch. This runbook leaves the port unchanged.

Backup / Recovery

The /etc/ssh backup contains host keys: encrypt it and restrict access. To roll back this change from the console or an open session, move out only the new snippet, validate and reload.

sudo mv /etc/ssh/sshd_config.d/00-enterprise.conf /root/00-enterprise.conf.failed
sudo /usr/sbin/sshd -t
sudo systemctl reload ssh.service

If existing settings were changed, restore their recorded backup. VM recovery must not create duplicate host keys across different servers.

Best Practices

Manage personal accounts, passphrases, departed staff keys and sudo reviews in one lifecycle. Before closing the last session, verify login, privileges and auditing through the real management path.

Legacy Versions and Compatibility

Do not apply Ubuntu commands unchanged to RHEL: the service is commonly sshd and the package manager differs. The old PermitRootLogin yes recommendation is retired for production. A restart does not necessarily terminate every established session; inspect daemon and systemd behavior separately.

Frequently Asked Questions

Is changing the SSH port enough?

No. Source restrictions, keys, account lifecycle controls and audit records are still required.

What must pass before password login is disabled?

Key login and sudo in an independent session, with console recovery available.
