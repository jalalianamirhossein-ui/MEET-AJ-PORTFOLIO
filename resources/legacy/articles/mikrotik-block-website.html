Block Domains on MikroTik: DNS and SNI Limits

Configure NXDOMAIN and tls-host rules, test DNS and TLS independently, and assess DoH, QUIC and ECH bypass limits.

MikroTik

Meet AJ technical article

Start reading

What domain filtering sees

For HTTPS sites, the router generally cannot read request content. DNS policy controls names at the resolver, while tls-host inspects visible SNI. Shared CDN addresses and names hidden by ECH limit these approaches.

Resolver and RouterOS requirements

Use RouterOS v7 and verify type=NXDOMAIN and match-subdomain on the selected patch. Do not assume identical syntax across all v7 releases.

Identify LAN/WAN membership and client IPv6 paths. Record CPU, connection tracking and FastTrack rules before the change.

Keep an off-router export and console access. Use router recursion only with permitted LAN DNS and blocked WAN DNS access.

Wildcards in DNS and address lists

An address-list value of *.example.com is not a general DNS wildcard. DNS match-subdomain and tls-host glob syntax have distinct behavior. Historical content rules are not modern HTTPS enforcement.

DNS policy and SNI filtering differ

NXDOMAIN rejects name resolution. Tls-host acts on TCP traffic with a visible ClientHello. QUIC uses UDP, ECH hides the name and VPNs change the path. Strict enforcement also needs endpoint and secure-web-gateway design.

Example: a managed-client policy

Users query an internal resolver and example.com is the test domain. Test DNS and TCP independently. Endpoint management controls DoH and VPN use. Router rules alone do not guarantee organization-wide enforcement.

Avoid open recursion and CDN collateral damage

Do not expose router DNS recursion to WAN. Scope resolver enforcement to user subnets with explicit exceptions. A CDN IP might host unrelated services, so avoid blocking it from one DNS answer. Generic Layer7 matching does not reliably inspect encrypted HTTPS content.

Configure the domain and test DNS/TLS separately

Record DNS/firewall state and verify LAN/WAN membership. Permit router TCP/UDP 53 from LAN only and prevent WAN recursion. 

/ip dns print
/ip firewall filter print detail
/ip dns static add name=example.com match-subdomain=yes type=NXDOMAIN comment="ENT-WEB DNS policy"
/ip firewall filter add chain=forward in-interface-list=LAN out-interface-list=WAN protocol=tcp dst-port=443 tls-host=example.com action=drop comment="ENT-WEB root SNI"
/ip firewall filter add chain=forward in-interface-list=LAN out-interface-list=WAN protocol=tcp dst-port=443 tls-host=*.example.com action=drop comment="ENT-WEB subdomain SNI"

Use an existing restricted resolver. Do not enable allow-remote-requests before firewall controls. Put SNI rules before relevant FastTrack/established accepts and test fresh connections. 

/ip firewall filter print stats where comment~"ENT-WEB"
/ip dns static print detail where comment~"ENT-WEB"

Test DNS and TCP TLS separately from a managed client. 

dig @10.20.30.1 example.com
curl --http1.1 --connect-timeout 5 https://example.com

Replace 10.20.30.1 with the actual resolver. Expect NXDOMAIN from dig. For SNI tests, resolve through an allowed DNS path and test TLS with the real name. Failed DNS does not prove a TLS match.

Measure user impact

Compare rule counters with actual client outcomes. Record UDP/443 volume, user reports and false positives. Test application fallback before blocking QUIC.

When the site still opens

Check root/subdomains and DNS caches first, then isolate DoH, QUIC, ECH, proxies and IPv6. A ClientHello split across TCP segments might not match. DNS failure does not establish SNI-rule effectiveness. Test it with permitted resolution and a fresh connection.

Prove DNS and SNI policy independently

A failed DNS query prevents any later TLS test, so it cannot prove SNI filtering. In an isolated managed client, first test example.com and a subdomain against the policy resolver and record NXDOMAIN. For a separate authorized SNI test, obtain a current server address through an approved alternate resolution path and use curl --resolve with the real hostname, forcing HTTP/1.1. Do not substitute the IP in the URL because that changes SNI and certificate-name validation. Compare a permitted control hostname; only the intended policy should fail. Recheck fresh connections, rule counters and IPv6 before acceptance.

# Replace documentation hostname/address with the authorized lab endpoint.
curl --http1.1 --connect-timeout 3 --max-time 10 --resolve example.com:443:203.0.113.20 https://example.com/

The documentation IP is not an Internet service. A timeout alone is inconclusive: inspect whether the intended SNI drop counter increments while the permitted control completes with valid TLS. ECH, QUIC, segmented ClientHello and VPNs remain limitations. Do not claim this policy blocks all HTTPS access to a brand or CDN.

Undo policy and handle caches

Disable ENT-WEB rules and DNS entries to undo this policy, leaving unrelated firewall configuration intact. 

/ip firewall filter disable [find where comment~"ENT-WEB"]
/ip dns static disable [find where comment~"ENT-WEB"]

Then clear relevant client/resolver caches through their supported methods and retest the application. Cached answers affect immediate test results.

Policy owners and exceptions

Specify domains, subdomains, user groups and authorized exceptions. Assess router filtering alongside endpoint management and a web gateway for organizational enforcement.

Frequently Asked Questions

Does tls-host block all HTTPS?

No. ECH, QUIC, fragmentation and VPNs limit its visibility.

Does one destination IP identify one website?

No. A CDN can share an IP across multiple services.
