MikroTik Web Access Policy: DNS, TLS SNI and HTTPS Limitations

Implement a scoped DNS/SNI policy and validate its limits with modern TLS, QUIC, ECH, DoH and managed endpoint controls.

MikroTik

Meet AJ technical article

Start reading

Introduction

IP blocking and string matching are unreliable for CDN-backed sites and modern TLS. A web policy must state its visibility limits and the expected behavior of managed clients.

Practical Example

User-VLAN clients use an internal resolver. example.com is the test target. The router supplies part of the policy; endpoint management governs DoH and VPN bypass.

Prerequisites

MikroTik RouterOS v7. Record the exact patch and architecture with /system resource print. Review v6 commands before using them on v7. Verify type=NXDOMAIN and match-subdomain support using CLI help on the selected patch.

Use a router or isolated CHR lab with separate interfaces. Measure CPU, RAM and connection tracking under representative load.

Connect from the management network with the required write policies. Before changing configuration, enable Safe Mode with Ctrl+X, save an off-device export and arrange independent console access.

Architecture / Design

Managed client → organizational resolver → DNS policy; observable TCP TLS → tls-host. QUIC, ECH and VPNs may hide the destination name from the router. A secure web gateway may still be required.

Installation / Configuration

Record DNS configuration and Firewall order. Verify LAN/WAN membership. Enable router recursion only where input permits LAN UDP/TCP 53 and blocks WAN access, with these rules placed before the final drop.

/ip dns print
/ip firewall filter print detail
/ip dns static add name=example.com match-subdomain=yes type=NXDOMAIN comment="ENT-WEB DNS policy"
/ip firewall filter add chain=forward in-interface-list=LAN out-interface-list=WAN protocol=tcp dst-port=443 tls-host=example.com action=drop comment="ENT-WEB root SNI"
/ip firewall filter add chain=forward in-interface-list=LAN out-interface-list=WAN protocol=tcp dst-port=443 tls-host=*.example.com action=drop comment="ENT-WEB subdomain SNI"

Use an already approved resolver; do not enable allow-remote-requests without the correct Firewall. Place SNI rules before relevant FastTrack and established accepts. Test fresh connections because existing FastTrack sessions can bypass the rules.

/ip firewall filter print stats where comment~"ENT-WEB"
/ip dns static print detail where comment~"ENT-WEB"

Test DNS and TCP TLS independently from a managed Linux client.

dig @10.20.30.1 example.com
curl --http1.1 --connect-timeout 5 https://example.com

10.20.30.1 is the router-resolver placeholder. Expect NXDOMAIN from DNS. For the SNI test, resolve through an allowed DNS path so TCP rejection can be measured; DNS failure alone does not prove the matcher works.

Security Hardening

Never expose DNS recursion on WAN. Scope enforced DNS to user subnets and approved resolvers, with documented datacenter/VPN exceptions. Avoid blanket CDN IP blocking. Encrypted HTTPS content is not reliably filtered by generic Layer7 rules.

Monitoring

Record policy counters, UDP/443 volume, CPU and user impact. Assess application fallback before blocking QUIC. Before-and-after charts should include authorized bypasses and false positives.

Troubleshooting

If a site opens, inspect root/subdomains, caches, DoH, ECH, QUIC, proxies and IPv6 separately. A fragmented ClientHello may not match tls-host. An IP rule may block unrelated CDN services; verify ownership and changing DNS results.

Backup / Recovery

Retain a policy export. Disable only the rules and DNS entries added by this change during rollback.

/ip firewall filter disable [find where comment~"ENT-WEB"]
/ip dns static disable [find where comment~"ENT-WEB"]

Clear client/resolver caches through the approved procedure and retest the application. Leave unrelated Firewall configuration intact.

Best Practices

Use endpoint management and a secure web gateway where organization-wide enforcement is required. Assign a business owner, documented exceptions and a review date.

Legacy Versions and Compatibility

An address-list entry containing *.example.com is not a general DNS wildcard. Historical content/Layer7 examples do not provide modern HTTPS enforcement. Verify NXDOMAIN and matchers on the exact patch.

Frequently Asked Questions

Does tls-host block all HTTPS?

No. ECH, QUIC, fragmentation and VPNs limit its visibility.

Does one destination IP identify one website?

No. A CDN can share an IP across multiple services.
