Ubuntu Server Netplan: Static IP Changes with Validation and Rollback

Change Ubuntu Server addressing through Netplan with IPAM checks, YAML ownership, client validation and console-based rollback.

Linux

Meet AJ technical article

Start reading

Introduction

An IP change over SSH can interrupt management, DNS and backup traffic together. Apply Netplan changes with explicit file ownership, preflight checks and confirmation from a separate client.

Practical Example

An application VM in VLAN 30 moves from DHCP to 10.20.30.10/24. NetBox holds the reservation, and networking has validated the trunk and ACLs.

Prerequisites

Ubuntu Server 24.04 LTS, Bash 5 and systemd. Record installed package patches with dpkg-query before making changes.

Example lab capacity: 2 vCPUs, 2 GiB RAM and 20 GiB storage. These are planning assumptions, not vendor minimums; size the service for measured load.

Use netplan.io and systemd-networkd with sudo, console access and an IPAM reservation. ens160, 10.20.30.10, gateway and DNS values form a complete lab example; replace them for your environment.

Architecture / Design

Netplan YAML → generator → systemd-networkd → NIC/VLAN → gateway. systemd-resolved owns DNS. Multiple YAML files merge; adding a new file does not automatically remove earlier settings.

Installation / Configuration

Record the current state from the console and back up the entire directory.

ip -br address
ip route
resolvectl status
sudo netplan get
sudo cp -a /etc/netplan /root/netplan-before-change

This configuration targets a single-NIC VM with one authoritative network file. Identify the active file and remove conflicting YAML ownership. If cloud-init generates it, transfer ownership deliberately or update the cloud configuration source.

sudo tee /etc/netplan/01-production.yaml >/dev/null <<'EOF'
network:
  version: 2
  renderer: networkd
  ethernets:
    ens160:
      dhcp4: false
      addresses: [10.20.30.10/24]
      routes:
        - to: default
          via: 10.20.30.1
      nameservers:
        addresses: [10.20.30.53, 10.20.30.54]
        search: [corp.example.com]
EOF
sudo chmod 600 /etc/netplan/01-production.yaml
sudo netplan generate
sudo netplan try --timeout 120

Before accepting netplan try, test the gateway, SSH and DNS from another client. Expect the specified address on ens160, only the intended default route and no generator errors. Test timeout rollback on the target platform; keep console recovery available rather than relying on it alone.

ip -br address show ens160
ip route get 10.20.30.53
resolvectl query corp.example.com
ping -c 3 10.20.30.1

Security Hardening

Mode 600 limits access to sensitive YAML content. A static IP does not replace a Firewall. Preserve internal DNS and management routing; a successful ping does not prove all services are available. Configure IPv6 according to organizational policy and evaluate its routes too.

Monitoring

Monitor availability, packet loss and address changes in Zabbix; node_exporter exposes interface errors to Prometheus. Alert networking on route changes or more than two consecutive missed polls. Run application health checks from the consumer subnet.

Troubleshooting

YAML errors commonly arise from indentation or tabs; generate identifies their location. Multiple default routes can come from merged files or remaining DHCP settings.

sudo netplan --debug generate
networkctl status ens160
sudo journalctl -u systemd-networkd -n 100 --no-pager
resolvectl status ens160

Correct IP with an unreachable gateway: inspect VLANs, mask and ARP. Working routing with broken DNS: inspect the resolver and port-53 ACLs. Settings that revert after reboot indicate cloud-init or automation still owns the configuration; correct its source.

Backup / Recovery

From the console, remove the new file and restore the previous YAML from backup. Do not blindly merge backups containing overlapping definitions.

sudo mv /etc/netplan/01-production.yaml /root/01-production.yaml.failed
sudo cp -a /root/netplan-before-change/. /etc/netplan/
sudo netplan generate
sudo netplan apply

Keep IPAM, VLAN and routing records outside the VM. After rollback, test access from both management and application subnets.

Best Practices

Do not change NIC, VLAN and IP simultaneously. Check address conflicts, keep a live console and validate a canary before accepting the rollout.

Legacy Versions and Compatibility

Replace older gateway4 examples with routes. Desktop deployments may use NetworkManager; this example uses networkd. netplan try has rollback limitations for some virtual-link configurations.

Frequently Asked Questions

Does netplan try guarantee recovery?

No. Review rollback limitations and retain an independent console.

Why do settings revert after reboot?

Cloud-init or a configuration management tool usually still generates the file.
