Set a Static IP on Ubuntu Server with Netplan

Inspect YAML ownership, configure routes and DNS, use netplan try, and diagnose failures with a rollback path.

Linux

Meet AJ technical article

Start reading

Change the IP while preserving access

Netplan generates Ubuntu networking from YAML. To move from DHCP to static addressing, prepare interface, prefix, gateway and DNS values. An SSH-based change risks the active connection. Console access and a second-client test are part of the procedure.

YAML, renderer and resolver

Netplan generates settings for the selected renderer. Here networkd manages interfaces and resolved handles DNS. A new file does not necessarily replace prior interface settings. Inspect the merged result with netplan get.

Example: a VM in VLAN 30

The VM moves from DHCP to 10.20.30.10/24 via 10.20.30.1. Exclude the address from DHCP allocation or reserve it correctly. Validate VLANs and management ACLs before changing it.

Interface and network-file ownership

Use Ubuntu 24.04 LTS with netplan.io and systemd-networkd. Confirm the actual interface instead of assuming ens160.

No particular VM allocation is required. IPAM, an active console and a test client matter. Match sample subnets and DNS to the actual network.

Inspect all of /etc/netplan. Do not manually overwrite cloud-init or automation output without changing its authoritative source. Multiple YAML files merge.

NetworkManager and rollback limitations

Use routes for the default route. Older gateway4 syntax is deprecated. Desktops might use NetworkManager. Try has rollback limitations around virtual links. After timeout, verify actual state and on-disk files.

Write YAML and confirm netplan try

Record the current state from the console and back up the entire directory. 

ip -br address
ip route
resolvectl status
sudo netplan get
sudo cp -a /etc/netplan /root/netplan-before-change

This configuration targets a single-NIC VM with one authoritative network file. Identify the active file and remove conflicting YAML ownership. If cloud-init generates it, transfer ownership deliberately or update the cloud configuration source. 

sudo tee /etc/netplan/01-production.yaml >/dev/null <<'EOF'
network:
  version: 2
  renderer: networkd
  ethernets:
    ens160:
      dhcp4: false
      addresses: [10.20.30.10/24]
      routes:
        - to: default
          via: 10.20.30.1
      nameservers:
        addresses: [10.20.30.53, 10.20.30.54]
        search: [corp.example.com]
EOF
sudo chmod 600 /etc/netplan/01-production.yaml
sudo netplan generate
sudo netplan try --timeout 120

Before accepting netplan try, test the gateway, SSH and DNS from another client. Expect the specified address on ens160, only the intended default route and no generator errors. Test timeout rollback on the target platform. Keep console recovery available rather than relying on it alone. 

ip -br address show ens160
ip route get 10.20.30.53
resolvectl query files01.corp.example.com
ping -c 3 10.20.30.1

Replace files01.corp.example.com with an existing internal DNS record. A zone’s existence does not guarantee an A record at its root.

Tests after the change and reboot

Test SSH from management and the application from its consumer subnet. Record IP, routes and DNS. Repeat after a controlled reboot to detect cloud-init or automation overwrites.

Valid YAML with broken networking

generate identifies syntax/indentation errors. Use spaces instead of tabs. Extra default routes might come from merged files or remaining DHCP. 

sudo netplan --debug generate
networkctl status ens160
sudo journalctl -u systemd-networkd -n 100 --no-pager
resolvectl status ens160

Correct IP with an unreachable gateway requires mask, VLAN and neighbor checks. Broken DNS with working routes calls for resolver and port-53 ACL checks. Settings reverting after boot require file-ownership investigation.

Restricted files and IPv6 paths

Use mode 600 because some network YAML contains secrets. Static IP does not replace a firewall. Check DNS, management and IPv6 paths too. A ping response establishes only that ICMP path.

Restore YAML through the console

From the console, move the new file out and restore prior YAML. Leave no overlapping extra file. Run generate before apply. 

sudo mv /etc/netplan/01-production.yaml /root/01-production.yaml.failed
sudo cp -a /root/netplan-before-change/. /etc/netplan/
sudo netplan generate
sudo netplan apply

After rollback, retest routes, DNS, SSH and the application. Keep VLAN/IPAM records outside the VM. Netplan try does not replace an independent console.

Change one part at a time

Avoid changing NIC, VLAN and IP simultaneously. Check address conflicts first. During try, test login/DNS from a second client and confirm only after success.

Frequently Asked Questions

Does netplan try guarantee recovery?

No. Review rollback limitations and retain an independent console.

Why do settings revert after reboot?

Cloud-init or a configuration management tool usually still generates the file.
