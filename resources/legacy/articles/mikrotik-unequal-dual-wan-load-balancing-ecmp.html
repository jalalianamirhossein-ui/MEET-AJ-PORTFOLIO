Unequal Dual-WAN Load Balancing with PCC on RouterOS v7

Build 2:1 connection classification, policy routing and NAT, test failover, and distinguish PCC from ECMP.

MikroTik

Meet AJ technical article

Start reading

Connection weighting is not bandwidth aggregation

For 100 and 50 Mbps links, PCC classifies new connections into three buckets. Two use WAN1 and one uses WAN2. Connection counts approach 2:1, but flow sizes differ and a single download does not aggregate both links.

Why the Configuration Uses PCC

Criterion ECMP PCC
Mechanism Route selection among equal-cost next hops Connection classification using hashes and marks
Distribution control Depends on routing and implementation hashing Designed through classifier buckets
Return paths NAT session return paths need separate validation Controlled through connection and routing marks

The original topic was unequal load balancing with failover using ECMP. That goal is retained. The RouterOS v7 configuration uses PCC for an explicit 2:1 bucket allocation and return-path policy. A connection ratio does not guarantee a bandwidth ratio. Test hashing, NAT and failover on the target version.

Connection marks and routing tables

PCC marks the connection, and its packets select the associated table. Inbound replies must use their ingress WAN. Internal bypass rules keep LAN and VPN destinations out of WAN policy routing.

Example addresses and interfaces

ether1/WAN1 uses 192.168.30.2/30 via 192.168.30.1. Ether2/WAN2 uses 172.30.30.2/30 via 172.30.30.1. Ether3 carries LAN 10.10.10.0/24. Replace these values from actual IPAM.

Before policy routing

This example uses RouterOS v7 syntax. Record the release and do not paste v6 route commands unchanged.

Preconfigure the lab interfaces and gateways. Check CPU and connection tracking under representative traffic. Classification depends on conntrack and marks.

Keep console access and an off-device export. The example assumes no existing DNAT or policy routing. Review production rules, VPNs and internal networks before adding marks.

Why the historical ECMP URL is retained

The historical URL preserves existing links, while this weighted example uses PCC. Repeating ECMP gateways is not a dependable 2:1 guarantee. In v7, create routing tables before referencing them.

Configure tables, mangle and NAT

Review the export, routes and FastTrack rules. Exclude marked connections during a canary deployment. An existing FastTrack rule can be temporarily disabled in the lab. 

/ip address print
/ip route print detail
/ip firewall mangle print detail
/ip firewall filter print where action=fasttrack-connection
/routing table add name=ent-wan1 fib
/routing table add name=ent-wan2 fib
/ip firewall address-list add list=ent-local address=10.10.10.0/24
/ip firewall address-list add list=ent-local address=192.168.30.0/30
/ip firewall address-list add list=ent-local address=172.30.30.0/30
/ip firewall mangle add chain=prerouting in-interface=ether3 dst-address-list=ent-local action=accept comment="ENT-PCC local bypass"
/ip firewall mangle add chain=prerouting in-interface=ether1 connection-state=new connection-mark=no-mark action=mark-connection new-connection-mark=ent-c1 comment="ENT-PCC incoming WAN1"
/ip firewall mangle add chain=prerouting in-interface=ether2 connection-state=new connection-mark=no-mark action=mark-connection new-connection-mark=ent-c2 comment="ENT-PCC incoming WAN2"
/ip firewall mangle add chain=prerouting in-interface=ether3 dst-address-type=!local connection-state=new connection-mark=no-mark per-connection-classifier=both-addresses-and-ports:3/0 action=mark-connection new-connection-mark=ent-c1 comment="ENT-PCC bucket0"
/ip firewall mangle add chain=prerouting in-interface=ether3 dst-address-type=!local connection-state=new connection-mark=no-mark per-connection-classifier=both-addresses-and-ports:3/1 action=mark-connection new-connection-mark=ent-c1 comment="ENT-PCC bucket1"
/ip firewall mangle add chain=prerouting in-interface=ether3 dst-address-type=!local connection-state=new connection-mark=no-mark per-connection-classifier=both-addresses-and-ports:3/2 action=mark-connection new-connection-mark=ent-c2 comment="ENT-PCC bucket2"
/ip firewall mangle add chain=prerouting in-interface=ether3 dst-address-type=!local connection-mark=ent-c1 action=mark-routing new-routing-mark=ent-wan1 passthrough=no comment="ENT-PCC route1"
/ip firewall mangle add chain=prerouting in-interface=ether3 dst-address-type=!local connection-mark=ent-c2 action=mark-routing new-routing-mark=ent-wan2 passthrough=no comment="ENT-PCC route2"
/ip firewall mangle add chain=output connection-mark=ent-c1 action=mark-routing new-routing-mark=ent-wan1 passthrough=no comment="ENT-PCC reply1"
/ip firewall mangle add chain=output connection-mark=ent-c2 action=mark-routing new-routing-mark=ent-wan2 passthrough=no comment="ENT-PCC reply2"
/ip route add dst-address=0.0.0.0/0 gateway=192.168.30.1 routing-table=main distance=1 check-gateway=ping comment="ENT-PCC main1"
/ip route add dst-address=0.0.0.0/0 gateway=172.30.30.1 routing-table=main distance=2 check-gateway=ping comment="ENT-PCC main2"
/ip route add dst-address=0.0.0.0/0 gateway=192.168.30.1@main routing-table=ent-wan1 distance=1 check-gateway=ping comment="ENT-PCC table1 primary"
/ip route add dst-address=0.0.0.0/0 gateway=172.30.30.1@main routing-table=ent-wan1 distance=2 check-gateway=ping comment="ENT-PCC table1 backup"
/ip route add dst-address=0.0.0.0/0 gateway=172.30.30.1@main routing-table=ent-wan2 distance=1 check-gateway=ping comment="ENT-PCC table2 primary"
/ip route add dst-address=0.0.0.0/0 gateway=192.168.30.1@main routing-table=ent-wan2 distance=2 check-gateway=ping comment="ENT-PCC table2 backup"
/ip firewall nat add chain=srcnat src-address=10.10.10.0/24 out-interface=ether1 action=masquerade comment="ENT-PCC nat1"
/ip firewall nat add chain=srcnat src-address=10.10.10.0/24 out-interface=ether2 action=masquerade comment="ENT-PCC nat2"

Run this on a clean lab with a secured Firewall. Merge with existing production rules and remove duplicate routes/NAT. Add VPN/datacenter subnets to ent-local. Generate hundreds of fresh connections: buckets 0+1 should approach twice bucket 2 in connection count, not necessarily bytes. Disconnect WAN1 in the lab and verify active routes in every table and new-connection success.

Healthy gateway, failed upstream

check-gateway=ping tests the immediate gateway only. Upstream ISP failure with a responding gateway leaves that route apparently healthy. Monitor external reachability, loss and latency per WAN. Recursive or multi-target probing needs separate design.

Uneven distribution and wrong return paths

For unexpected distribution, inspect fresh connections and FastTrack. Wrong-WAN replies require connection marks and prerouting/output counters. Inactive routes need main-table next-hop and scope checks. Pin destinations sensitive to public-IP changes or test a more suitable classifier and remeasure distribution.

NAT and internal paths

NAT does not grant access. Keep WAN input default-deny and permit only approved forwarding. Include internal/VPN subnets in bypass policy. Existing DNAT needs independent return-path tests.

Rollback and session behavior during failover

Rollback disables ENT-PCC mangle, restores prior routes/NAT and disables new rules. Remove tables after references are gone. Avoid blindly clearing conntrack. A public-IP change commonly requires existing TCP sessions to reconnect.

Test every table with fresh connections

Generate hundreds of fresh connections and compare bucket connection counts. Fail WAN1 and WAN2 independently and inspect every table’s active route and new-connection success. Gateway and upstream failure are different tests.

Frequently Asked Questions

Does 2:1 weighting guarantee a 2:1 bandwidth ratio?

No. Weighting applies to connections whose flow sizes differ.

Does failover preserve TCP sessions?

A changed public IP can terminate a session and require reconnection.
