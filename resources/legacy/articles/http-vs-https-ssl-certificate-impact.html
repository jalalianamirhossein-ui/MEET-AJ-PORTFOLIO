HTTP vs HTTPS: TLS Certificates and Troubleshooting

Compare HTTP and HTTPS, verify certificates with OpenSSL and curl, and introduce HSTS in stages.

What HTTPS protects

HTTP carries web requests and responses. HTTPS protects that exchange with TLS against reading or modification in transit and lets the client authenticate the server. Invalid certificates or incomplete chains interrupt that verification.

HTTP vs HTTPS in Practice

CriterionHTTPHTTPS
Transport confidentialityTraffic is not encryptedTLS protects the connection
Server authenticationThe protocol does not authenticate the serverCertificate names and trust chains are validated
Transport integrityNo TLS protectionTLS detects modification in transit
Conventional port80. Other ports are possible443. Other ports are possible
Operational requirementsNo TLS certificate lifecycleRenewal, trust stores and expiry monitoring

HTTPS protects transport. It does not fix application vulnerabilities, incorrect permissions or account theft. A valid certificate does not establish the quality or legitimacy of a business. The original article uses the familiar term SSL, while current deployments use TLS.

From DNS to the HTTP request

The client locates the destination and verifies its certificate and name during the TLS handshake. HTTP follows. When a proxy terminates TLS, design protection for its backend connection separately.

Example: move an API to HTTPS

Prepare DNS and a matching certificate for the internal API, then test real clients on staging. Once TLS and application requests pass, introduce redirects and HSTS in stages.

Tools for inspecting TLS

Diagnostics use Ubuntu 24.04 LTS, OpenSSL 3 and curl. Proxy configuration uses Nginx. Match TLS 1.2 and 1.3 support to real clients.

The comparison has no VM sizing requirement. For an actual service, measure TLS overhead and concurrent connections alongside application load.

Replace app.example.com with your domain. Its certificate needs matching SANs and a valid chain. Restrict the private key and install any internal CA in the client trust store.

Older clients and HSTS policy

TLS 1.2 and 1.3 differ in ciphers and handshakes. Check older clients’ supported versions and algorithms. Browsers acquire HSTS through trusted HTTPS. A redirect alone does not protect the initial HTTP request.

Verify the certificate and introduce HSTS

Replace app.example.com with the actual endpoint. Verify its certificate using OpenSSL/curl without bypasses.

HOST='app.example.com'
openssl s_client -connect "$HOST:443" -servername "$HOST" -verify_hostname "$HOST" -verify_return_error </dev/null
curl --fail --show-error --head "https://$HOST/"

Check Verify return code: 0 (ok), a matching name and the expected response. For internal CAs use a trust store or --cacert with a trusted file. -k removes this trust test.

The Nginx guide in this library provides complete TLS configuration. Add this directive inside its HTTPS server block. It is not a standalone configuration.

add_header Strict-Transport-Security "max-age=300" always;
sudo nginx -t
sudo systemctl reload nginx
curl --fail --head https://app.example.com

Expect the header on HTTPS with a short max-age. Extend duration after hostname and renewal tests. IncludeSubDomains/preload require complete inventory and recovery planning.

Monitor the certificate actually served

Probe names, chains and expiry through the real client path. A valid disk file does not prove the service loaded it. Alerts at 30, 14 and 7 days are examples. Include an API request to distinguish application failures from TLS failures.

Diagnose certificate and browser failures

For expiry, inspect notAfter and the client clock. For name mismatch, compare SAN, SNI and DNS. Unknown issuers require intermediate and trust-store checks. Browser-only failures require mixed-content, HSTS and browser CA checks. OpenSSL without verification-error stopping options might continue with warnings.

TLS protection boundaries

SSL is common terminology, but SSLv2 and SSLv3 are unsuitable for new services. HTTPS does not repair vulnerable application logic or compromised clients. Restrict keys, use a fixed trusted redirect hostname and assess replay risks before 0-RTT for state-changing requests.

Renewal and HSTS recovery

Back up keys, certificates and configuration securely. Reload after renewal and probe the served certificate. Removing HSTS requires delivering max-age=0 over valid HTTPS. Offline clients do not receive that policy immediately. Preload removal has a separate process and delay.

Test trust without bypasses

Assign certificate ownership and renewal procedures. Do not use curl -k for acceptance. Supply internal CAs through a trust store or trusted CA file to exercise the actual trust path.

Frequently Asked Questions

Does redirect replace HSTS?

No. Browsers acquire HSTS policy through trusted HTTPS.

Why is a valid certificate on disk insufficient?

The service may still serve an older certificate. Probe from the real client path.
