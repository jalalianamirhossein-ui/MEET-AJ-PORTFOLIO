RouterOS v7 OpenVPN: PKI, Least-Privilege Access and TLS Diagnostics

Configure a version-pinned OpenVPN service with individual certificates, matching client settings, return routes and tested forward ACLs.

MikroTik

Meet AJ technical article

Start reading

Introduction

A working tunnel without forward controls can expose more of a datacenter than the client needs. Validate authentication, return routing and service authorization together.

Practical Example

Support can reach only SSH on 10.20.30.10. Clients use dedicated certificates, a separate 10.250.0.0/24 pool and split tunneling.

Prerequisites

RouterOS 7.17 or later with named servers; OpenVPN Community 2.6 on Linux/Windows. Pin the selected patch after staging validation.

Use a router or isolated CHR lab with separate interfaces. Measure CPU, RAM and connection tracking under representative load.

Connect from the management network with the required write policies. Before changing configuration, enable Safe Mode with Ctrl+X, save an off-device export and arrange independent console access. Use an existing organizational PKI with a CA, a vpn.example.com server certificate with SAN and individual client certificates. Time synchronization and TCP/1194 reachability are required.

Architecture / Design

Client certificate + PPP user → TCP/1194 → OpenVPN server → pool → forward ACL → server. LAN routing must return 10.250.0.0/24 traffic through this router. NAT does not replace correct return routing.

Installation / Configuration

Upload ca.crt and server.p12 from the PKI to Files. Import the private key from a password-protected file; do not keep the CA private key on the edge router.

/system clock print
/certificate import file-name=ca.crt passphrase=""
/certificate import file-name=server.p12 passphrase="REPLACE_WITH_P12_SECRET"
/certificate print detail

Inspect imported names and replace REPLACE_SERVER_CERT with the actual certificate name. Confirm its private key and valid chain.

/ip pool add name=ent-ovpn-pool ranges=10.250.0.10-10.250.0.100
/ppp profile add name=ent-ovpn local-address=10.250.0.1 remote-address=ent-ovpn-pool
/ppp secret add name=opsvpn service=ovpn password="REPLACE_WITH_UNIQUE_USER_SECRET" profile=ent-ovpn
/interface ovpn-server server add name=ent-ovpn-server disabled=no protocol=tcp port=1194 mode=ip certificate=REPLACE_SERVER_CERT require-client-certificate=yes auth=sha256 cipher=aes256-cbc tls-version=only-1.2 default-profile=ent-ovpn
/ip firewall filter add chain=input in-interface-list=WAN protocol=tcp dst-port=1194 action=accept comment="ENT-OVPN listener"
/ip firewall filter add chain=forward src-address=10.250.0.0/24 dst-address=10.20.30.10 protocol=tcp dst-port=22 action=accept comment="ENT-OVPN SSH grant"
/ip firewall filter add chain=forward src-address=10.250.0.0/24 action=drop comment="ENT-OVPN deny other"

Place rules before the final drop and before broad LAN accepts. Existing established/related handling must permit responses. This example assumes an already secured Firewall with default deny.

Save the complete client.ovpn beside ca.crt, client.crt and client.key. Replace vpn.example.com with the real name covered by the certificate. Protect the client key with a passphrase.

client
dev tun
proto tcp-client
remote vpn.example.com 1194
nobind
persist-key
persist-tun
ca ca.crt
cert client.crt
key client.key
auth-user-pass
remote-cert-tls server
verify-x509-name vpn.example.com name
tls-version-min 1.2
auth SHA256
cipher AES-256-CBC
data-ciphers AES-256-CBC
route 10.20.30.10 255.255.255.255
verb 3

On Linux, sudo openvpn --config client.ovpn should report Initialization Sequence Completed. Enter login and key passwords interactively. Test both permitted SSH and denied destinations.

Security Hardening

Disable compression. Give each client a separate identity; revoke both certificate and PPP credentials during offboarding. require-client-certificate alone does not bind a certificate to a username. Verify that mapping through policy and negative tests. MFA needs a compatible RADIUS/identity design and is not implemented here.

Monitoring

Monitor active PPP sessions, pool utilization, certificate expiry, failed authentication and tunnel logs. Distinguish an individual disconnect from a service outage. An expiry alert below 30 days is an example threshold.

Troubleshooting

For TLS verification failure, inspect time, CA, SAN and key usage. For AUTH_FAILED, check PPP service, password and policy. For SSH timeout on an established tunnel, inspect return routing and forward counters. Match this CBC/SHA256 baseline exactly; do not add GCM without validating compatibility.

Backup / Recovery

Keep an export without secrets, encrypted backups and PKI material in a vault. Test client revocation and CRL behavior on the chosen patch. Rollback disables the named server and ENT-OVPN rules and removes dedicated client routes; one-rule changes need not restore the whole router.

Best Practices

Validate routing, authentication, positive ACLs and negative ACLs in sequence. Allocate a certificate and account per client. The cipher is a compatibility baseline subject to the organization’s cryptographic policy.

Legacy Versions and Compatibility

Versions before 7.17 use different singleton-server syntax. UDP and cipher support vary by version. The historical SHA1/AES-GCM combination was incompatible. The router’s own IP must not be its default-route gateway.

Frequently Asked Questions

Why can the tunnel connect while SSH fails?

Return routing and forward ACLs are independent of authentication.

Do all v7 patches use identical configuration?

No. Named-server configuration changed in 7.17; pin and validate the target patch.
