Set Up OpenVPN on RouterOS v7 with Restricted Access

Configure a named server, certificates and an OpenVPN 2.6 client, then verify return routing and service ACLs.

MikroTik

Meet AJ technical article

Start reading

A tunnel is not an access policy

OpenVPN connects a client to a private network, but a working tunnel does not define its authorization scope. This example permits support access to one server’s SSH only. Test certificates, PPP authentication, return routing and forward ACLs together.

VPN forward and return paths

After certificate and PPP checks, pool traffic passes through forward ACLs. Destination routing must return the pool through this router. Include the pool in any source-restricted server SSH policy. NAT that hides missing routes is not the default design.

Example: split-tunnel SSH to one server

The pool is 10.250.0.0/24 and the permitted destination is 10.20.30.10. The client receives only that host route. Allocate individual accounts/certificates and replace addresses with your IP plan.

Version, PKI and management access

Named-server syntax targets RouterOS 7.17 onward. The client example uses OpenVPN Community 2.6. Test and record the selected router/client patches before deployment.

Measure router CPU, tunnel count and throughput under load. Avoid overlap with LAN or other VPN pools. This example uses TCP/1194.

Existing PKI supplies CA, server and client certificates. Match the real server name in SAN and, for this example, CN as well, because verify-x509-name checks the subject name. Keep correct clocks, console access and off-router backups.

RouterOS versions and transport differences

Before 7.17, servers used different singleton syntax. UDP and cipher support depend on release. TCP here targets compatibility, but TCP-over-TCP suffers under loss. Validate UDP against both peers and firewall policy before selecting it.

Individual certificates and revocation

Leave compression disabled and assign individual credentials. Require-client-certificate alone does not bind a certificate to a specific username. Negatively test identity mapping. Revoke PPP access, certificates and sessions during offboarding. MFA requires a compatible identity/RADIUS design beyond this example.

Import certificates and configure server/client

Upload ca.crt and server.p12 from the PKI to Files. Import the private key from a password-protected file. Do not keep the CA private key on the edge router. 

/system clock print
/certificate import file-name=ca.crt passphrase=""
/certificate import file-name=server.p12 passphrase="REPLACE_WITH_P12_SECRET"
/certificate print detail

Inspect imported names and replace REPLACE_SERVER_CERT with the actual certificate name. Confirm its private key and valid chain. 

/ip pool add name=ent-ovpn-pool ranges=10.250.0.10-10.250.0.100
/ppp profile add name=ent-ovpn local-address=10.250.0.1 remote-address=ent-ovpn-pool
/ppp secret add name=opsvpn service=ovpn password="REPLACE_WITH_UNIQUE_USER_SECRET" profile=ent-ovpn
/interface ovpn-server server add name=ent-ovpn-server disabled=no protocol=tcp port=1194 mode=ip certificate=REPLACE_SERVER_CERT require-client-certificate=yes auth=sha256 cipher=aes256-cbc tls-version=only-1.2 default-profile=ent-ovpn
/ip firewall filter add chain=input in-interface-list=WAN protocol=tcp dst-port=1194 action=accept comment="ENT-OVPN listener"
/ip firewall filter add chain=forward src-address=10.250.0.0/24 dst-address=10.20.30.10 protocol=tcp dst-port=22 action=accept comment="ENT-OVPN SSH grant"
/ip firewall filter add chain=forward src-address=10.250.0.0/24 action=drop comment="ENT-OVPN deny other"

Place rules before the final drop and before broad LAN accepts. Existing established/related handling must permit responses. This example assumes an already secured Firewall with default deny.

Save the complete client.ovpn beside ca.crt, client.crt and client.key. Replace vpn.example.com with the real name covered by the certificate. Protect the client key with a passphrase. 

client
dev tun
proto tcp-client
remote vpn.example.com 1194
nobind
persist-key
persist-tun
ca ca.crt
cert client.crt
key client.key
auth-user-pass
remote-cert-tls server
verify-x509-name vpn.example.com name
tls-version-min 1.2
auth SHA256
cipher AES-256-CBC
data-ciphers AES-256-CBC
route 10.20.30.10 255.255.255.255
verb 3

On Linux, sudo openvpn --config client.ovpn should report Initialization Sequence Completed. Enter login and key passwords interactively. Test both permitted SSH and denied destinations.

From TLS errors to SSH timeouts

For TLS errors, inspect clocks, CA, CN/SAN and key usage. AUTH_FAILED points to PPP service, password or policy. Healthy tunnels with SSH timeouts require return-route, forward-counter and server-firewall checks. Match cipher/SHA256 settings on both sides. Adding GCM without version/auth validation is not a generic repair.

Pool, sessions and certificate expiry

Monitor active PPP sessions, pool use, authentication failures and certificate expiry. Distinguish one user’s disconnect from listener failure. Allow enough expiry-warning time for issuance and deployment.

Revocation and configuration rollback

Protect secret-free exports, encrypted backups and PKI material. Test CRL enforcement on the selected patch using a revoked certificate. Rollback disables the named server, ENT-OVPN rules and associated client routes. A single-rule change does not require whole-router restore.

Test forbidden access too

Test forbidden destinations and ports alongside permitted SSH. Router counters must agree with the results. This compatibility-oriented cipher choice requires organizational cryptographic-policy review.

Frequently Asked Questions

Why can the tunnel connect while SSH fails?

Return routing and forward ACLs are independent of authentication.

Do all v7 patches use identical configuration?

No. Named-server configuration changed in 7.17. Pin and validate the target patch.
