Install Nested ESXi in Workstation and Diagnose VMCISr

Configure nested virtualization, install a lab ESXi host and diagnose VMCI failures using logs and exact builds.

What nested ESXi is useful for

Nested ESXi runs as a VM inside Workstation. It suits virtual-network and API rehearsal, but successful installation establishes neither production support nor hardware performance. Diagnose pre-power-on VMCISr failures from that VM’s logs.

CPU, host and compatible builds

Use ESXi 8.x and Workstation compatible with the host OS. Record exact versions and the full error. Check applicability before borrowing another build’s workaround.

The example host has 32 GiB RAM, SSD and VT-x/EPT or AMD-V/RVI. Allocate four vCPUs, 8 GiB RAM and suitable boot/datastore disks to ESXi. These allocations are not speed guarantees.

Enable virtualization in host firmware and expose the required guest features through Workstation. Keep administrator/console access and a valid image.

Nested support limitations

This workflow is for a lab. Check Broadcom’s nested-support conditions. VMCISr names the failing module rather than one universal cause across versions.

Two virtualization layers

Workstation exposes CPU features to ESXi, which uses them for its guest VMs. Booting ESXi alone does not prove nested virtualization is available to those guests. Boot a small nested VM too.

Example: rehearse a vSwitch change

Build one ESXi host with two small nested VMs. Keep management host-only and provide required outbound access through NAT. This keeps test traffic out of the company LAN.

Host security during workarounds

Use lab-specific credentials and keep management off the Internet. When a KB calls for Hyper-V, VBS or Secure Boot changes, check its build scope and security impact. Disabling host controls is not a general nested-error fix.

Build the ESXi VM and test Host Client

Enable host-firmware virtualization and select Virtualize Intel VT-x/EPT or AMD-V/RVI in VM CPU settings. Record Workstation and host-OS versions.

Select the ESXi guest type and image-compatible adapter. Attach a valid ISO, verify the dedicated target disk, then install ESXi.

Use DCUI F2 → Configure Management Network for IP, DNS and hostname. Replace the sample host-only 10.99.0.11/24 to match VMnet. Run Test Management Network.

Test TCP/443 from the workstation with this command. 

Test-NetConnection -ComputerName 10.99.0.11 -Port 443

TcpTestSucceeded: True establishes TCP reachability only. Open Host Client and verify the lab certificate fingerprint through the console. Then boot a small nested VM and test its network/storage.

Host and guest resource pressure

Inspect host RAM, ESXi swapping and disk latency. Slow lab guests might reflect host oversubscription. Record results with the allocated resources.

Investigate VMCISr and VT-x failures

For Module VMCISr power on failed, inspect the VM folder’s vmware.log, VMCI settings and the matching-build KB. Deleting vmci0 is not a version-independent fix. For unavailable VT-x, check firmware, nested settings and the host virtualization engine. Missing NICs require adapter/image compatibility checks, not arbitrary driver injection.

Collect the exact power-on failure on the Windows host

Replace the path with this powered-off VM’s actual folder. Read its log before editing VMX. The block is Windows PowerShell, runs on the Workstation host and makes no VM configuration change. A missing vmware.log calls for checking the actual VM folder and most recent power-on attempt.

$VmFolder = 'D:\LabVMs\NestedESXi'
Get-ChildItem -LiteralPath $VmFolder -Filter 'vmware*.log' | Select-Object Name,Length,LastWriteTime
Get-Content -LiteralPath (Join-Path $VmFolder 'vmware.log') -Tail 100
Select-String -LiteralPath (Join-Path $VmFolder 'vmware.log') -Pattern 'VMCISr','VMCI','VT-x','AMD-V','MonitorMode'

Expected: timestamped context around the actual failed module or CPU virtualization limitation. No match is not proof of support. Match the exact host, Workstation and ESXi builds to the vendor KB; preserve a powered-off VMX copy before any documented workaround and undo only that change if it fails. Never blindly delete VMCI entries or disable host security controls.

Restore VMX and lab data

Keep a copy of the powered-off VM and VMX. Undo VMX edits only while powered off, using the recorded copy. Application data inside nested guests needs in-guest backups too. Lab snapshots do not replace them.

Record reproducible failures

Record the error, host/Workstation/ESXi builds and CPU settings together. Apply each workaround independently and repeat power-on and nested-guest boot tests.

Frequently Asked Questions

Is nested ESXi on Workstation supported for production?

Check the vendor support matrix. This procedure covers a lab only.

Does deleting a device always fix VMCI failures?

No. Establish the cause using logs and the build-specific KB.
