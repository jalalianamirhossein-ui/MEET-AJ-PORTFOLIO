Nested ESXi on VMware Workstation: Deployment and VMCI Diagnostics

Validate nested ESXi in an isolated lab and investigate VMCI errors using exact build information, logs and vendor compatibility guidance.

VMware

Meet AJ technical article

Start reading

Introduction

Nested ESXi is useful for migration/API rehearsal, but does not establish bare-metal performance or support. Diagnose VMCI failures from logs and build compatibility.

Practical Example

Before changing a vSwitch, the team builds a nested ESXi host and two test VMs. Management is isolated from the company LAN.

Prerequisites

ESXi 8.x with an authorized ISO and a Workstation build compatible with the host OS. Record exact versions and the applicable error KB before changes.

Suggested lab host: 32 GiB RAM, VT-x/EPT or AMD-V/RVI CPU and SSD. Allocate 4 vCPU, 8 GiB RAM, a suitable boot disk and separate datastore to nested ESXi. These are not performance guarantees.

Enable firmware virtualization; provide administrative Workstation/console access and separate Host-only/NAT networks. Use valid software licenses.

Architecture / Design

Physical CPU → Workstation virtualization engine → nested ESXi → nested VM. Nested workloads cannot boot if the host hypervisor does not expose their required features.

Installation / Configuration

Record Workstation and OS versions. Enable firmware virtualization and select Virtualize Intel VT-x/EPT or AMD-V/RVI in VM Settings.

Create a VM with the appropriate VMware ESXi guest type and a supported adapter for that build. Attach the official ISO and install to a verified dedicated disk.

Configure management IP, DNS and hostname through DCUI. The sample 10.99.0.11/24 belongs to Host-only and must match VMnet. Use F2 → Configure Management Network → Test Management Network.

From the workstation, test TCP connectivity and then Host Client.

Test-NetConnection -ComputerName 10.99.0.11 -Port 443

Expect TcpTestSucceeded: True, then open https://10.99.0.11/. Verify the lab certificate fingerprint against the console. Create a small nested VM and validate boot, networking and storage; Host Client alone is insufficient.

Security Hardening

Keep management off the public Internet and use separate lab credentials. Do not disable host VBS, Hyper-V or Secure Boot for a workaround without assessing its security impact and build support.

Monitoring

Record host resources, guest ballooning/swapping, datastore latency and Workstation logs. Separate lab alerts from production. Lab oversubscription is not evidence of a production architecture defect.

Troubleshooting

For Module VMCISr power on failed, inspect this VM’s vmware.log, devices and exact-build KB. Removing vmci0 or editing VMX is not a version-independent fix. For unavailable VT-x, check firmware, nested-feature exposure and the active host engine. For missing NICs, check adapter/image compatibility rather than injecting arbitrary drivers.

Backup / Recovery

Back up the powered-off VM, configuration/VMX and host configuration export. A snapshot is useful before tests but does not replace in-guest backups for stateful nested workloads. Roll back VMX workarounds only while powered off, using the recorded version.

Best Practices

Document lab and production scope. Record exact errors/builds in support tickets and apply workarounds only to KB-covered versions.

Legacy Versions and Compatibility

Broadcom documents nested ESXi support restrictions. Successful Workstation installation does not establish production support. VMCISr is a symptom with multiple possible causes.

Frequently Asked Questions

Is nested ESXi on Workstation supported for production?

Check the vendor support matrix; this procedure covers a lab only.

Does deleting a device always fix VMCI failures?

No. Establish the cause using logs and the build-specific KB.
