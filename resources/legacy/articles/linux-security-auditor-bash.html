Building an Enterprise Linux Security Auditor with Bash

Read the Linux Security Auditor 2.0.0 architecture, severity-weighted scoring, SSH, patch, firewall and container checks, with practical CLI examples and limits.

Security review beyond SSH and a firewall

An SSH key and an active firewall are useful controls, but they do not describe the whole server. An extra UID 0 account, writable service unit, stale security repository or missing audit trail can undermine that baseline. A useful audit connects identity, configuration, running state and the evidence that remains unavailable.

Review authentication, users, password policy and sudo alongside SSH, host filtering, listening sockets and patch management. Filesystem permissions, cron, persistence, systemd, kernel settings, logging, audit rules, AppArmor or SELinux, containers and threat indicators each answer a different operational question.

This article follows the actual security-audit.sh version 2.0.0. Enterprise here means explicit scope, evidence, prioritization and reviewable reports. It is not a claim that a single Bash script replaces a security program.

What the auditor does and how its engine works

The tool is a single-file GNU/Linux posture assessor requiring Bash 4.4 or newer. Modules collect bounded command snapshots and file metadata. They emit records with stable check IDs, category, state, severity, expected and actual values, evidence, risk, evaluation method and a recommended action. The action is text for an operator, not a remediation command that runs automatically.

The final emit and calculate functions define the version 2 engine. Do not infer scoring from the early legacy category-weight declarations. The active categories are System, Authentication, PAM, Sudo, SSH, Network, DNS, Firewall, Patching, Filesystem, Permissions, Persistence, Systemd, Kernel, MAC, Logging, Audit, Cryptography, Containers, Threat, Recovery, Resources and Cloud.

Records also identify automated_check, inventory, manual_evidence_required or coverage. A record count is not a count of successfully verified controls. Missing commands, denied access, timeouts and unavailable external evidence remain visible as UNKNOWN rather than becoming a pass.

External commands normally have a 12-second limit. File scans default to 30 seconds each. Quick skips selected expensive scans and package integrity verification. Standard bounds selected scans to depth 6; deep expands candidate local mount roots and package verification. Pattern scans retain their own depth and size bounds even in deep mode. --full changes terminal detail, whereas --profile full changes selected policy controls.

OS detection and the honest support matrix

OS fields are parsed from /etc/os-release without sourcing or evaluating the file. ID selects Debian/APT, RHEL/DNF with YUM fallback, or SUSE/ZYPPER; ID_LIKE can select a family for an otherwise unknown ID. A recognized family does not automatically make the release a validated target.

The validation matrix lists partial support for Ubuntu 20.04, 22.04, 24.04 and 26.04; Debian 11, 12 and 13; RHEL, Rocky, AlmaLinux and Oracle Linux 8, 9 and 10; CentOS Stream 9 and 10; and openSUSE Leap/SLES 15 and 16 families. The SUSE code accepts broader version strings, but that must not broaden the documented validation matrix. Other releases receive generic observations without distribution assurance.

No distribution is fully validated across every subsystem. The documented native run used an Ubuntu 24.04 container as root in quick and standard modes. OS fixtures test dispatch, not real SELinux, firewall, boot or package-manager integration. Stage the tool on the actual host family before fleet use.

Severity-weighted score and evidence coverage

Scored controls use severity weights: CRITICAL 10, HIGH 6, MEDIUM 3 and LOW 1. Explicit weight-zero records remain unscored. PASS earns full weight, WARN earns half, and FAIL earns zero. UNKNOWN is removed from the known-score denominator but remains in the applicable-weight denominator used for coverage. NA and INFO are excluded from both.

text
raw_score = floor(100 * (PASS_weight + 0.5 * WARN_weight) / known_weight)
coverage  = floor(100 * known_weight / applicable_weight)
score     = min(raw_score, critical_cap)

For example, a HIGH pass (6), MEDIUM warning (3), LOW failure (1) and HIGH unknown (6) produce 75 raw points and 62% coverage. Integer arithmetic truncates percentages. Category points use the same formula within each category. The overall score is pooled across control weights, not an average of category percentages. One, two or at least three critical findings cap it at 85, 75 or 65 by default.

The verdict prioritizes critical findings, then high findings, then coverage below 80%. With enough coverage and no high or critical findings, at least 85 points yields STRONG OBSERVED BASELINE; otherwise IMPROVEMENT REQUIRED. A high score with low coverage is incomplete evidence. It is not a percentage of being unhackable or a substitute for a penetration test.

The CIS-aligned value is a separate unweighted pass/assessed ratio for selected aligned controls. Benchmark coverage is also separate. Attack-surface points pool Network, Firewall, SSH and Containers. Threat score starts at 100 and subtracts twice each warning/failure weight tagged Threat Indicator, down to zero; inspect threat coverage beside it. Neither this value nor an empty indicator list establishes incident clearance.

Status and severity are different fields

Internal states are PASS, WARN, FAIL, UNKNOWN, NA and INFO. Public status maps WARN to WARNING and NA to NOT_APPLICABLE. A FAIL with HIGH or CRITICAL severity becomes that public status; a LOW or MEDIUM failure becomes WARNING. Therefore a public WARNING can still carry HIGH severity. Read status, severity and evidence together.

Severity accepts CRITICAL, HIGH, MEDIUM, LOW and INFO. PASS means the observed local condition met its stated expectation. INFO records context; UNKNOWN records an evidence gap; NOT_APPLICABLE can mean an absent component or exclusion by profile. None of these labels should be read without scope.

Download, requirements and first execution

Download the actual source below, review it, and transfer it to the intended Linux host. No installer or package installation step is built in. Required standard utilities are awk, grep, sed, find, stat, df, timeout, mktemp, tr, cut, head, sort, wc, date and readlink. Optional inspection commands vary by subsystem. Missing optional evidence usually becomes UNKNOWN.

Download security-audit.sh (v2.0.0)

bash
chmod +x security-audit.sh
./security-audit.sh --version
./security-audit.sh --help
sudo ./security-audit.sh --quick --summary
sudo ./security-audit.sh

The default is standard cost, enterprise profile and summary output. A non-root run is allowed but shadow, firewall, audit and cross-user metadata may be unreadable. Root inside a container still lacks host namespaces and capabilities. Deep scans can consume I/O even though they do not remediate anything.

Each export target and output directory must be new. Parent directories must already exist, contain no symlink components and, for root exports, be trusted root-owned paths; writable non-sticky ancestors are rejected. Use a fresh /root report name. JSON and HTML can use relative filenames, but sudo does not change the working directory, so a relative export in an untrusted directory can fail. --export-html without a filename also defaults under the working directory.

Exit 0 means no HIGH/CRITICAL findings and at least 80% coverage, not a guaranteed score threshold. Exit 1 means high or critical findings; 2 means incomplete assessment; 3 means usage or runtime failure; 130 and 143 mean interruption. The risk exit takes precedence over incomplete coverage. Automation should retain the report and branch on these outcomes rather than treating every nonzero exit as a crash.

Read the dashboard from context to priority findings

The terminal dashboard shows hostname, OS, kernel, UTC timestamp, distribution family, package manager, architecture, virtualization, uptime, privilege mode, primary IP, MAC and firewall summaries. It then displays capped posture points, raw points, evidence coverage, severity counts and per-category points and coverage.

System health reports maximum local disk and inode use plus memory pressure. Summary prints up to eight priority findings ordered CRITICAL, HIGH, MEDIUM, LOW and up to five unknown gaps. Findings include evidence and action text. --full adds all controls and technical metadata. Color and bar rendering adapt to terminal capabilities, width and UTF locale, with an ASCII fallback.

JSON uses schema_version 2 and includes audit, host, scores, summary, categories, findings and bounded inventory. Finding status, internal state and severity are separate. When no scored evidence exists, scores.security is null, although compatibility aliases and terminal points can still be numeric. HTML has embedded responsive and print CSS, escaped evidence, a CSP and no external assets. The report directory also receives a detailed plain text report.

Patch management from cached evidence

On Debian-family hosts, apt-get simulates upgrade with locking and package-cache writes disabled. Inst rows count pending upgrades; security-origin text flags security-pocket candidates without assigning CVE severity. The newest Packages index timestamp is a freshness heuristic: more than seven days is adverse, a future timestamp is unknown, and a recent index does not prove every repository is current.

APT checks also cover dpkg --audit diagnostics, held packages, effective apt-config unattended-upgrade settings, insecure trust overrides, trusted source patterns, error-log indicators and apt-daily-upgrade.timer. Configured automation does not prove successful execution. History-log modification time is inventory, not evidence that a security update succeeded.

RHEL-family queries use DNF or YUM with --cacheonly and --noplugins, redirecting log and state paths to private temporary storage. check-update exit 100 is handled as available updates. updateinfo security rows are advisory/package candidates, not unique CVEs. Repository inventory, exclusions and signature-bypass patterns are inspected. Empty or unavailable security metadata remains UNKNOWN; cache completeness and subscription require independent evidence.

SUSE runs cached zypper queries only when root can use bwrap with a read-only root mount and isolated network namespace. --no-refresh alone is insufficient because libzypp can rebuild caches. Without that sandbox or a usable cache, results remain UNKNOWN. Repository reachability is never tested.

Reboot evidence is distribution-specific: Debian uses /run/reboot-required, RPM may use needs-restarting -r, and SUSE reboot status remains unknown. Running kernel and /boot images are inventoried. Debian compares installed package versions only within the running kernel flavor. RPM flavor/EVR correlation, including Oracle UEK/RHCK, is not guessed. SUPPORT_END may provide a local lifecycle hint, but extended entitlement, livepatch, current CVEs and overdue critical advisories remain separate questions.

Local users, password policy, PAM and sudo

Account checks use local passwd, group and shadow: extra UID 0 accounts, duplicate UIDs/GIDs, interactive service accounts, empty password fields, legacy or unrecognized hash formats, aging and expiry. Supported hash classifications include yescrypt, SHA-512 crypt and listed bcrypt prefixes. Hash values are neither exported nor cracked. A locked password does not revoke an SSH key or every PAM path.

Interactive home existence, ownership and broad permissions are checked, together with .netrc, .rhosts and .forward indicators, shell-history access and .ssh permissions. Authorized-key metadata is assessed without exporting key contents. External directory users and centrally enforced policies are outside this local identity inventory.

PAM module references cover hashing, history, lockout, quality enforcement for root and nullok candidates. pwquality and faillock numeric settings are inventory because includes, snippets and module arguments may override them. The script does not reconstruct the complete effective PAM stack. Password aging is an organizational policy question, not proof of password strength.

visudo -c validates sudoers syntax when available. Pattern checks flag NOPASSWD or disabled authentication, unrestricted ALL, wildcards, interpreter/editor delegation and SETENV candidates. use_pty, secure_path, logfile and timestamp_timeout references are inventoried without resolving all include order and defaults. Review effective privileges per administrative role before changing access.

SSH effective configuration and Match scope

The auditor asks sshd -T for parsed effective settings. This is more useful than grepping one sshd_config file because the daemon applies defaults and configuration includes. A selected -C context also evaluates relevant Match rules. Without context, the report explicitly leaves Match and daemon-scope coverage unknown.

bash
sudo ./security-audit.sh --ssh-context 'user=admin,host=admin.example,addr=192.0.2.10' \
  --sshd-config /etc/ssh/sshd_config --full

Replace the example identity, hostname and source address with actual administrative contexts. Audit every allowed role and source range, plus separate sshd instances and custom daemon flags. One successful context is not global SSH assurance.

Checks include root/password/empty-password login, public keys, X11, gateway ports, host-based authentication, rhosts, user environment, authentication attempts and selected legacy crypto patterns. Extended checks cover MaxSessions, LoginGraceTime, StrictModes, alive interval/count, and selected Level 2 tunnel, logging and user-rc restrictions. MaxStartups and identity/MFA directives are inventoried. Root password login becomes critical only when the selected SSH settings and an active local root hash meet the implemented combination.

A password-authentication warning is not an instruction to disable keyboard-interactive blindly: that path may implement MFA. Missing sshd tooling is not proof of insecure settings. Keep a tested administrative session and validate policy compatibility before applying any separately approved hardening.

Firewall evidence and network exposure

UFW, nftables, iptables-save and ip6tables-save provide local rule inventories when readable. The auditor checks active UFW incoming defaults and simple broad allow patterns, inventories nft hooks and legacy base policies, and notes duplicate literal iptables rules and concurrent manager indicators. A ruleset being present is not a proof of an effective packet verdict; chain order, priorities, sets, jumps and NAT still matter.

ss collects listening TCP/UDP sockets and established connections; ip supplies interfaces and IPv4/IPv6 routes. Non-loopback default-port candidates identify legacy services and databases/caches for review, without proving the protocol or authentication. Socket owners may need root. Custom ports can evade these port lists.

Listening on 0.0.0.0 or :: means a wildcard bind in the observed namespace. It does not establish public internet exposure. NAT, cloud security groups, load balancers, upstream firewalls, routing and source policy determine actual reachability. IPv6 enforcement parity and external reachability remain UNKNOWN because no external probe or cloud API request is performed. Verify both address families from an authorized external vantage point.

Cron, startup paths and systemd persistence

The script inspects system cron paths and per-user spool paths, local systemd directories, rc.local and ld.so.preload permissions. It inventories timers, running/enabled services, failed units, reboot jobs and deferred at jobs. Cron command bodies are withheld from reports because they may contain credentials; the auditor never runs discovered jobs.

Bounded pattern scans flag download-to-shell, execution from temporary storage, base64 decode-to-execution, hidden script paths, reverse-shell syntax and system shell startup injection candidates. Recent modification times are context, not an unauthorized-change verdict. Without an approved baseline, the auditor cannot decide whether a job or timer is unauthorized.

A sample of up to 30 running services records root/default users, local unit fragments and writable fragments. systemd-analyze security supplies a bounded sandbox summary when available. Its exposure values are hardening suggestions, not vulnerability scores. User units, drop-ins, executables and deployment records still need a complete operator review.

Filesystem, permissions and capacity

Permission checks inspect owner and mode bits for passwd/group, shadow/gshadow and backups, sudoers fragments, cron directories, PAM, SSH configuration fragments, bootloader files, logging/audit configuration and other privileged paths. The masks express this tool’s baseline, not every vendor exception. Missing paths can be not applicable; unreadable protected paths are unknown.

Bounded local scans find world-writable regular files, unmapped ownership, SUID/SGID files, large files, sensitive filename permission candidates and hidden executables. SUID/SGID is an inventory requiring comparison with a trusted package baseline, not automatic evidence of a vulnerability. Credential filename checks inspect metadata rather than secret contents. Network filesystems are inventoried and excluded from file scans.

findmnt resolves the containing mount for paths such as /tmp, /var/tmp and /dev/shm, so a nonexistent separate partition is not invented. Sticky bit, nodev, nosuid, noexec and selected separate-mount policies are evaluated with profile and host-role exceptions. Mount restrictions can break workloads and must be tested separately.

df -P -l and df -Pi -l record maximum local disk and inode use. Default thresholds are strictly above 80, 90 and 95 percent, so exactly 90 does not cross the HIGH threshold. A timed-out or inaccessible scan with no matches is inconclusive. Partial matches can produce an additional coverage record instead of silently claiming the whole scope passed.

Kernel hardening checks and role-dependent settings

The base sysctl checks expect randomize_va_space=2, kptr_restrict=2, dmesg_restrict=1, protected_hardlinks=1, protected_symlinks=1, tcp_syncookies=1 and suid_dumpable=0. ptrace_scope accepts the baseline 1 and stricter observed values 2 or 3. IPv4 all/default accept_redirects, send_redirects and accept_source_route, plus IPv6 all/default accept_redirects and all accept_source_route, are checked against zero.

Extended checks cover protected_fifos/protected_regular >=1, unprivileged_bpf_disabled >=1, perf_event_paranoid >=2, default rp_filter >=1, all/default log_martians=1, broadcast/bogus ICMP protections=1 and IPv4 secure_redirects=0 plus IPv6 default accept_source_route=0. Level 2 adds user namespaces=0, IPv6 router advertisements/forwarding=0 and sysrq=0. core_uses_pid=1 is also inspected.

The tool observes all.rp_filter, IPv4 forwarding, lockdown, Secure Boot hints, boot security-bypass/debug patterns and selected optional module resolution. modprobe --show-depends does not load or unload modules. Routers, VPNs, containers and asymmetric routing can need different settings; assess those exceptions before remediation. The script never writes sysctls.

Logging, auditing and trustworthy time

The auditor checks journald state, the persistent journal directory, /var/log permissions, rsyslog service and remote-forwarding indicators, logrotate.timer and configuration permissions. It inventories conventional authentication logs, world-writable logs and recently empty files. A journal directory does not establish effective retention; an empty file may be normal rotation. Remote SIEM delivery and unexplained gaps remain unknown without external receipt and an event baseline.

auditd activity is separate from rule coverage. auditctl -s supplies enabled, lost and backlog_limit, with event loss receiving an adverse result. auditctl -l is checked for patterns covering identity, sudo, login/logout, privileged execution, module, clock, network and MAC changes. Matches are not proof of complete semantics, architecture coverage or delivered events. Root may still lack CAP_AUDIT_CONTROL.

timedatectl synchronization and chronyc tracking offset/leap fields provide time evidence. The audit does not initiate an NTP probe. Validate the actual daemon and approved sources, since inaccurate time affects event correlation and package-index age interpretation.

AppArmor and SELinux without assuming missing means disabled

RHEL-family detection selects SELinux as the expected MAC; other families default to AppArmor, with observed SELinux enforcing/permissive state adjusting the selection. getenforce and /etc/selinux/config distinguish runtime and configured mode. Policy type, recent AVC indicators and unconfined service contexts are inspected. Denials are counted without exporting audit records or automatically generating allow rules.

aa-status provides AppArmor enabled and loaded/enforced/complain/unconfined counts when readable. Complain profiles need review, and loaded profiles do not prove every service is confined. Missing inspection commands become UNKNOWN or NOT_APPLICABLE according to scope, not an automatic disabled verdict. Confirmed disabled expected MAC can become critical outside the explicitly handled docker/lxc environments.

Docker and Podman through existing local APIs

Docker is queried through /var/run/docker.sock with an isolated client configuration. Podman uses its existing service Unix socket, /run/podman/podman.sock for root or the selected user runtime socket without root. The local Podman storage CLI is avoided because it may initialize storage. Remote daemon contexts are not inherited, and the tool does not start a missing Podman service.

Up to 100 running containers are sampled for privileged mode, host network/PID/IPC, root or unspecified user, SYS_ADMIN/ALL/SYS_PTRACE capabilities, writable root filesystem, missing no-new-privileges, runtime socket mounts, host-root/sensitive/writable host mounts, published ports and unconfined security options. Names, environment and command arguments are not collected. Missing or partially readable runtime evidence is explicit.

API socket permissions, exited-container counts, insecure-registry configuration candidates and port 2375/2376 listener candidates add host context. A world-writable runtime socket is critical. Published ports do not prove internet exposure, and those TCP ports do not prove an unauthenticated Docker API. Image currency remains UNKNOWN or not applicable: image age cannot establish vulnerabilities. Use a separate approved image scanner and registry policy.

Threat indicators, cryptography and recovery gaps

Threat paths observe /proc executable links, deleted-but-running executables, temporary/home execution, writable root-owned running files, shell processes owned by web identities, mining-name patterns and hidden executables. CPU and memory snapshots describe health. Software upgrades can explain deleted executables; deployment tasks can explain temporary binaries. These are investigation leads, not a malware diagnosis or forensic clearance.

Standard mode verifies selected core packages; deep uses broader dpkg -V or rpm -Va --noscripts. Changed configuration files may be legitimate, and local package metadata may itself be tampered with. Independent signed baselines and EDR/SIEM correlation are needed for stronger assurance.

Crypto checks inventory OpenSSL vendor version, flag selected legacy TLS/cipher configuration patterns and inspect up to 100 public .crt files in /etc/ssl/certs outside quick mode for expiry and 30-day expiry candidates. Trust-store certificates are not necessarily served certificates. No live TLS handshake is performed, and private-key contents are not opened by this certificate path. Credential filename and cloud-init permission candidates likewise require local confirmation.

Cloud identification uses DMI hints without calling metadata endpoints. IMDS/IAM policy, actual disk encryption coverage, backup recoverability and workload security remain manual evidence gaps. A backup agent or recent backup filename cannot prove an off-host copy or a working restore.

Read-only design and private evidence

The auditor does not refresh repositories, install or upgrade packages, change firewall rules, chmod/chown audited files, restart services, load/unload modules or write sysctls. The chmod command in the setup example is an operator action to make the downloaded script executable. It is not host remediation by the auditor.

Read-only refers to inspected configuration and workloads, not zero filesystem writes. umask 077, a private temporary directory under /tmp and requested private reports are part of normal execution. Temporary files are cleaned on exit; reports remain. Self-test also writes isolated fixtures. No network probes or package downloads run, though local daemon sockets are used for container inspection.

Reports can contain hostnames, accounts, paths and network metadata. Bounded inventories redact selected comments and descriptions; process arguments, environments and cron command bodies are withheld. Redaction is not permission to publish a report. Keep it in approved private storage and share only the evidence needed for a remediation ticket.

Validation evidence and what remains unverified

The supplied VALIDATION.md records a passing bash -n check and isolated self-test with 22 OS detection fixtures, color/ASCII, scoring, status mapping, JSON, temporary-path and utility/privilege checks. It reports a historical 67-test regression suite, but that suite and the claimed live report/catalogue files are not included in the supplied two-file package. These historical results are documented evidence, not a new run performed by this article.

bash
bash -n security-audit.sh
./security-audit.sh --self-test

ShellCheck was unavailable in the documented environment, so no successful ShellCheck result is claimed. Native non-root integration and syscall-level tracing were blocked; browser-rendered verification of exported HTML was also unavailable there. On an appropriate Linux staging host, rerun syntax/self-test, validate actual distro commands, and optionally run shellcheck security-audit.sh when installed. The command is a suggested next check, not evidence that it already passed.

The observed registry lists 427 records: 108 inventory, 293 automated checks, 24 manual-evidence gaps and 2 coverage records. Those are scoped observations, not a guaranteed fixed count per run. The historical summary contains many UNKNOWN results and two HIGH findings. A risk exit 1 is expected in such a run; it is not evidence of a crash or a verdict on your own server.

Limits and an operational review workflow

This is not a full CVE scanner, penetration test, certified CIS Benchmark assessment or malware detector. Selected CIS labels lack verified official section mappings. Profiles choose a local policy subset and can exclude relevant controls. Compliance, attack-surface and threat values always need their coverage and scope alongside them.

A compromised host may lie through its tools or local metadata. Point-in-time snapshots are not continuous monitoring. Timeouts, namespace boundaries, absent utilities, distribution differences and root capability restrictions limit conclusions. Public reachability, application authentication, vendor backports, subscription and recovery cannot be inferred from a few local settings.

Begin with quick mode on a staging host, then run standard with a fresh private report directory. Record version, profile, privilege, timestamps and gaps. Triage critical/high evidence against the real server role, open reviewed remediation tasks, and collect external evidence for unknown controls. After approved changes, rerun with the same profile and scope and compare both coverage and findings, not only the headline score.

Frequently asked questions

Does the auditor change server configuration?

It creates private temporary files and requested reports. It does not upgrade packages, change firewall rules or permissions, restart services, or write sysctls.

Does a score of 100 mean the server cannot be compromised?

No. Points describe observed controls within the selected scope. Unknown evidence reduces coverage, and external exposure, CVEs and recovery need separate validation.

Is this a certified CIS Benchmark assessment?

No. The profiles select locally implemented CIS-aligned controls. Official benchmark section mappings and certification are not claimed.

Turn findings into reviewed infrastructure work

For Linux administrators, DevOps, security and infrastructure engineers, the useful output is a defensible list of observations, risks and unanswered questions. The script makes a broad local review repeatable while keeping configuration changes outside the audit. Use its evidence to prioritize work, validate exceptions and ask for the external checks that a host-only assessment cannot supply.
