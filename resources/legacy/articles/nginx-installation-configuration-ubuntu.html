Production Nginx: Reverse Proxy, TLS and Upstream Troubleshooting

Deploy Nginx with a complete TLS reverse proxy, bounded timeouts, independent upstream checks, monitoring and validated reloads.

Linux

Meet AJ technical article

Start reading

Introduction

A healthy Nginx process does not prove the application is healthy. A reverse proxy needs bounded timeouts, request IDs, valid TLS and independent upstream checks so 502 failures can be traced.

Practical Example

An internal application listens on loopback and clients reach only the TLS proxy. Changes reach one canary VM before the Load Balancer.

Prerequisites

Ubuntu Server 24.04 LTS, Bash 5 and systemd. Record installed package patches with dpkg-query before making changes.

Example capacity: 2 vCPUs and 2 GiB RAM. Determine worker and file-descriptor settings through load testing. A working backend at 127.0.0.1:8080 is required.

Use sudo, nginx, curl and DNS for the placeholder app.example.com. Provision a valid certificate chain and private key from organizational PKI at the paths below.

Architecture / Design

Client → TCP/443 Nginx → loopback HTTP:8080 → application. For multi-host deployments, move the upstream to a private subnet with restricted Firewall access. Do not trust forwarding headers from arbitrary proxies.

Installation / Configuration

Check the backend first and preserve existing configuration. Install the package from the operating system repository.

sudo apt-get update
sudo apt-get install -y nginx curl
nginx -v
curl --fail --max-time 5 http://127.0.0.1:8080/health
sudo cp -a /etc/nginx /root/nginx-before-change

The health endpoint must return HTTP 200 and its expected application payload. Before writing configuration, install the certificate chain and private key below; the key must have root ownership and mode 600.

sudo tee /etc/nginx/sites-available/enterprise-app >/dev/null <<'EOF'
server {
    listen 80;
    server_name app.example.com;
    return 301 https://app.example.com$request_uri;
}
server {
    listen 443 ssl;
    server_name app.example.com;
    ssl_certificate /etc/nginx/tls/fullchain.pem;
    ssl_certificate_key /etc/nginx/tls/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Request-ID $request_id;
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
    }
}
EOF
sudo ln -s /etc/nginx/sites-available/enterprise-app /etc/nginx/sites-enabled/enterprise-app
sudo nginx -t
sudo systemctl reload nginx
curl --fail --max-time 10 https://app.example.com/health

Create the symlink only on first installation; inspect its existing destination otherwise. nginx -t must report syntax is ok and test is successful. Point canary DNS or --resolve at the canary VM. Resolve existing default-host or server_name conflicts before reloading.

Security Hardening

Do not bind the backend to a public IP. Protect the private key from ordinary users. Permit management traffic and 443 through the Firewall; port 80 is only needed for redirects or ACME. Trial HSTS with a short max-age and no includeSubDomains. Tune rate limits to paths and measured traffic rather than copied values.

Monitoring

Expose the Prometheus exporter only to monitoring. Track 5xx rate, upstream latency, handshake failures and certificate age. A 5xx rate above 1% for five minutes is an example threshold, subject to baseline. Grafana should show total and successful requests together, with request IDs in logs.

Troubleshooting

502 indicates failed connectivity or an invalid upstream response; 504 indicates a timeout; 403 points to permissions or policy. Test the upstream directly first.

curl --verbose --max-time 5 http://127.0.0.1:8080/health
sudo ss -lntp
sudo tail -n 80 /var/log/nginx/error.log
sudo journalctl -u nginx -n 50 --no-pager
sudo nginx -T

connect() failed with Connection refused identifies a missing backend listener. permission denied may involve a socket or AppArmor; chmod 777 is not a fix. nginx -T can expose sensitive configuration, so record it only in a protected location.

Backup / Recovery

Back up /etc/nginx and certificate secrets with restricted access. Application data and databases need separate backups. For rollback, restore the previous enterprise-app file, run nginx -t and reload. On first deployment, remove only the new symlink and validate the prior configuration. Stop/start is not the normal rollback mechanism.

Best Practices

Reload only after syntax checks, health tests and explicit acceptance criteria. Coordinate global worker changes with service limits and benchmark results.

Legacy Versions and Compatibility

This example uses listen 443 ssl for Ubuntu-package compatibility. HTTP/2 syntax differs between Nginx branches. The previous ellipsis-based example is not executable configuration and remains only in historical material.

Frequently Asked Questions

Does nginx -t verify application health?

No. It validates configuration; application health needs a separate check.

Should a 504 be fixed by increasing the timeout?

Inspect upstream latency and dependencies first; a longer timeout can increase queueing.
