vSphere Standard Switch vs Distributed Switch: Features and Design Choices

Compare vSS and vDS management, VLANs, traffic shaping, LLDP and port groups, then choose a design and validate migration without losing management access.

VMware

Meet AJ technical article

Start reading

Introduction

Both switch types connect VMs and VMkernel adapters to the network. Their management model and feature set differ. In a cluster, inconsistent VLANs or policies can break connectivity after a VM moves. This comparison explains those differences, selection criteria and configuration checks before covering migration.

How vSS and vDS Work

A vSS has an independent configuration on each ESXi host. Destination hosts need matching port groups, VLANs and policies. Matching port-group names alone do not prove matching settings.

A vDS is managed through vCenter while member hosts maintain the forwarding components. Distributed port groups define shared port policies. A vCenter outage generally leaves existing forwarding running, while restricting configuration changes and some recovery operations.

Port Groups, Uplinks and VMkernel

Port groups define connection policies for VMs or VMkernel adapters. Uplinks connect virtual switches to physical NICs. ESXi names physical NICs vmnic and VMkernel adapters vmk. The name vmk0 alone does not identify a service; inspect the actual Management, vMotion or storage configuration.

When to Choose vSS or vDS

Choose vSS for independent hosts, simple policies or designs without vCenter, provided the team can maintain consistency. Choose vDS when centralized management, shared policies or features such as LLDP, private VLANs and inbound shaping meet a real requirement. Include operational complexity, entitlement and recovery access in the decision.

If the comparison favors vDS, apply the configuration and migration procedure below to a canary host. Migration follows the architecture decision; it is not a prerequisite for using VLANs or vMotion.

Practical Example

Consider six ESXi hosts sharing application VLANs but carrying inconsistent port-group policies. Central management through vDS is a candidate for this cluster. A standalone host with ordinary VLAN and NIC teaming requirements may remain on vSS. Host count alone does not determine the choice.

Prerequisites

vSphere/ESXi 8.x. Confirm compatible vCenter builds and entitlement for vDS/features before design.

Two independent uplinks for this migration example, with consistent physical trunks and MTU. Retain one management uplink on vSS until validation.

vCenter Network configuration permissions and OOB access to each host. LACP requires compatible vDS/physical-switch support and explicit design.

Architecture / Design

vSS stores local configuration per host. vDS uses vCenter-managed control plane and host dataplanes. A vCenter outage does not necessarily stop existing forwarding, but constrains changes and recovery.

Installation / Configuration

Inventory each host’s vSS, port groups, VLANs, MTU, vmk interfaces and uplinks. Run these read-only ESXi Shell checks.

esxcli network vswitch standard list
esxcli network vswitch standard portgroup list
esxcli network ip interface list
esxcli network nic list

Create a vDS compatible with the oldest host. Define management, VM and vMotion distributed port groups with exact VLAN/MTU values. Align security and teaming with the baseline.

Move only the canary’s second uplink to vDS and place a test VM on the destination port group. Check VLAN, DNS and application reachability.

With OOB ready, migrate management vmk through Add and Manage Hosts. Retain the original vSS uplink until management is accepted. Test the gateway using the actual vmk.

vmkping -I vmk0 -c 3 10.20.30.1

vmk0 and the gateway are design placeholders. Test larger MTU end to end with an appropriate DF probe. Move the remaining uplink only after host/vCenter access stabilizes; do not change a second host before accepting the canary.

Security Hardening

Enable promiscuous mode, MAC changes or forged transmits only for documented workload needs. Separate network roles from general Administrator access and protect vDS backups/console credentials.

Monitoring

Alert on host disconnects, uplink failures, VLAN/MTU drift and packet drops. Collect LACP state and physical-switch errors from networking. LLDP/CDP use depends on topology-disclosure policy.

Troubleshooting

A disconnected VM with healthy vmk suggests VLAN, dvPort or VM policy. For host disconnect, inspect uplink mapping and management VLAN through OOB. Single-host problems suggest trunk/baseline drift. An MTU mismatch may pass small packets while breaking storage or vMotion.

Backup / Recovery

Export vDS/host configuration and back up vCenter before migration. For lost management, use vendor-documented DCUI/OOB network recovery to return vmk to a known vSS/port group. Supply local operators with previous uplink/VLAN names. vCenter must not be the sole recovery path.

Best Practices

Change one host and one uplink at a time. Prove rollback before removing the final vSS uplink. LACP alone does not guarantee application redundancy.

Legacy Versions and Compatibility

vSS supports VLANs and NIC teaming; vDS adds centralized features. Verify LACP/NIOC availability against edition and current contract.

Frequently Asked Questions

Does vSS support VLANs and NIC teaming?

Yes. Both switch types support these capabilities. Key vDS differences include centralized management, LLDP, private VLANs and inbound traffic shaping.

Does every cluster require vDS?

No. Feature requirements, configuration consistency, entitlement and recovery access determine the choice. A cluster can also use consistently configured standard switches.

Does a vCenter outage stop existing vDS traffic?

Existing host forwarding generally continues, while configuration changes and some recovery operations are restricted. Prepare OOB access and an independent recovery path.
